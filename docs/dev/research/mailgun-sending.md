# Research (planning, verified 2026-09-22): Mailgun HTTP API for sending: endpoints, auth, message parameters, custom Message-ID, unsubscribe/List-Unsubscribe, tracking-off, test mode, limits, crash reconciliation, SDK vs fetch (checked 2026-09-22)

Collected before the plan was written. Re-verify anything marked UNVERIFIED before relying on it.

## Summary

I checked everything against the official docs (the documentation.mailgun.com .md pages, the published OpenAPI YAML and help.mailgun.com articles). Sending is POST {base}/v3/{domain}/messages as multipart/form-data. The base URL is https://api.mailgun.net for US or https://api.eu.mailgun.net for EU, chosen by the region the domain was created in. Auth is HTTP Basic with username "api" and the API key as password. A 200 response returns {id, message}: id is the Message-ID in angle brackets and message is "Queued. Thank you.". Other responses: 400 means a validation failure (permanent), 429 means rate limited with X-RateLimit-* headers, and 500 means retry.

We can set our own Message-ID with h:Message-Id. The official FAQ and a help article both say "Mailgun will automatically include a unique Message-ID or you can set your own", and the merged Ghost PR confirms in practice that the custom ID is used in delivered mail and events. There is NO idempotency support for sends. The only idempotency key (o:inbox-placement-test-key) applies to Inbox Placement tests, and Ghost saw an identical resubmission accepted and delivered twice. So the crash-safe dedupe has to be ours: store the Message-ID before the POST, then check it afterwards through the Logs API (POST /v1/analytics/logs, filtering on message_id). The old GET /v3/{domain}/events endpoint is officially deprecated in favour of the Logs API.

Unsubscribe: turn on domain-level unsubscribe tracking (PUT /v3/domains/{d}/tracking/unsubscribe) and put %unsubscribe_url% in our own text and HTML footer. Mailgun then adds both List-Unsubscribe and List-Unsubscribe-Post: List-Unsubscribe=One-Click, but ONLY if the message does not already have a List-Unsubscribe header, so we must not set h:List-Unsubscribe ourselves. The unsubscribe links live on the tracking CNAME host, so that CNAME is required, and RFC 8058 requires an HTTPS URL, so the tracking host needs web_scheme=https and a cert.

Open and click tracking are switched off at domain level (PUT /v3/domains/{d}/tracking/open and /click with active=false) and per message (o:tracking-opens=no, o:tracking-clicks=no). With click tracking off, Mailgun does not rewrite links.

Test mode (o:testmode=yes) accepts the message and does not deliver it. It still emits a 'delivered' event with code 650 and flags.is-test-mode=true, and it IS billed.

Sandbox domains can only send to up to 5 verified authorized recipients. New accounts can be held to limits such as 100 messages/hour until Mailgun's business verification is done.

How long Logs/Events are kept depends on the plan (Free/Basic 1 day, Foundation 5 days, Scale 30 days). This matters for catching up after the PC has been off, so the suppression lists (bounces, unsubscribes, complaints), which do not expire, must be the main catch-up source.

Biggest non-technical risk: Mailgun's Acceptable Use Policy requires "clear, explicit and provable consent" for non-transactional mail and bans scraped or bought lists. Cold outreach is therefore at risk of account suspension, and the owner has to accept that risk knowingly. We should keep sending behind a provider adapter so another provider can be swapped in.

SDK choice: mailgun.js 14.0.1 works (it accepts Node's built-in FormData, takes url for EU, and has useFetch), but I recommend a small in-house client using Node 24's built-in fetch and FormData. That means no extra dependencies (the SDK pulls in axios) and full control over timeouts, 429 parsing and the unknown-outcome state.

## Facts

- REST base URLs: US https://api.mailgun.net , EU https://api.eu.mailgun.net (use the region the domain was created in). EU equivalents: SMTP smtp.eu.mailgun.org, inbound MX mxa.eu.mailgun.org / mxb.eu.mailgun.org, open/click/unsubscribe tracking CNAME target eu.mailgun.org (US: mailgun.org). Message data, event logs, suppressions, routes, webhooks and tags are region-bound; API keys and account data are global. — https://documentation.mailgun.com/docs/mailgun/api-reference/api-overview
- Auth: HTTP Basic, username 'api', password = API key (curl --user 'api:YOUR_API_KEY'). Header: Authorization: Basic base64('api:'+key). — https://documentation.mailgun.com/docs/mailgun/api-reference/mg-auth
- Key types: an Account API key can do all CRUD on every endpoint and every domain. A Domain Sending Key can ONLY make POST calls to /v3/{domain}/messages and /messages.mime for its own domain, so it cannot call Logs, suppressions, tracking settings or webhooks. RBAC key roles are Admin, Developer, Support and Analyst; in POST /v1/keys the role values are 'admin', 'basic' (instead of analyst), 'sending' (for kind=domain) and 'developer'. RBAC keys are available on Foundation, Scale, Contract and Enterprise. A key's role cannot be changed after creation. — https://documentation.mailgun.com/docs/mailgun/user-manual/api-key-mgmt/rbac-mgmt
- RBAC Developer role has Read/Write on Domains, Messages, Webhooks, Logs, Unsubscribes/Complaints/Bounces suppressions, Routes, Validations, Secure Tracking (only Read on Custom Message Limit, Credentials, Keys). — https://help.mailgun.com/hc/en-us/articles/26016288026907-API-Key-Roles
- POST /v3/{domain_name}/messages (multipart/form-data). Required: from, to, subject, plus one of text / html / amp-html / template. Other fields: cc, bcc, attachment, inline, template, t:version, t:text, t:variables, o:tag, o:dkim, o:secondary-dkim, o:secondary-dkim-public, o:deliverytime, o:deliver-within, o:deliverytime-optimize-period, o:time-zone-localize, o:testmode, o:tracking, o:tracking-clicks, o:tracking-opens, o:require-tls, o:skip-verification, o:sending-ip, o:sending-ip-pool, o:tracking-pixel-location-top, o:archive-to, o:suppress-headers, o:inbox-placement-test-key, h:<Header>, v:<var>, recipient-variables. All o:, h:, v: and t: parameters together are limited to 16KB. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/messages/post-v3--domain-name--messages
- Enum values: o:testmode = 'yes' (the user manual says 'yes' or 'true'); o:tracking and o:tracking-clicks = yes|no|true|false|htmlonly; o:tracking-opens = yes|no|true|false; o:require-tls and o:skip-verification = yes|no|true|false. o:require-tls defaults to 'no' (tries TLS, falls back to plaintext); o:skip-verification defaults to false. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/messages/post-v3--domain-name--messages
- o:deliverytime is in RFC-2822 format (e.g. 'Fri, 14 Oct 2011 12:00:00 +0000'). It can be up to 3 or 7 days ahead depending on plan, or limited by the domain's message_ttl. o:deliver-within limits the retry window, format [0-9]+h[0-9]+m, minimum 5m, maximum 24h. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/messages/post-v3--domain-name--messages
- h:<Header> adds any custom MIME header, e.g. h:Reply-To='reply@x.tld' (Reply-To is explicitly documented), h:In-Reply-To and h:References (generic custom headers). — https://help.mailgun.com/hc/en-us/articles/4401814149147-Reply-To-Addresses
- Custom Message-ID is supported. The official FAQ and help article both say: 'Mailgun will automatically include a unique Message-ID or you can set your own.' Pass it as h:Message-Id with angle brackets, e.g. '<id@sending-domain>'. — https://documentation.mailgun.com/docs/mailgun/faq/tracking
- (UNVERIFIED) Observed by others (Ghost PR #30776, merged 2026-09-16, tested on a Mailgun sandbox): with h:Message-Id set to '<%recipient.message_id%>', the delivered events showed the custom per-recipient IDs, and the API response id echoed the literal header value it was given. An identical resubmission with the same Message-IDs was 'Accepted' and Gmail delivered both copies, so Mailgun does NOT dedupe by Message-ID. — https://github.com/TryGhost/Ghost/pull/30776
- No idempotency support for sends. The only idempotency key in the whole OpenAPI spec is o:inbox-placement-test-key, which only stops duplicate Inbox Placement tests. — https://documentation.mailgun.com/_bundle/docs/mailgun/api-reference/send/mailgun.yaml
- 200 response body: {"id": "<20151025002517.117282.79817@sandbox-123.mailgun.org>", "message": "Queued. Thank you."}. id is the Message-ID WITH angle brackets. In events and webhooks, message.headers.message-id appears WITHOUT brackets, e.g. '20241218224823.5db69a3fac199381@dev.example.com'. — https://github.com/mailgun/mailgun.js
- Error responses are JSON {message}. The OpenAPI 400 examples include 'to parameter is not a valid address...' and 'Send options (parameters starting with o:, h:, or v:) are limited to 16KB total'. A 401 has the body 'Forbidden'. The 429 example is 'Domain example.com is not allowed to send: account-requests-per-sec limit exceeded, try again after 120 seconds'. — https://documentation.mailgun.com/_bundle/docs/mailgun/api-reference/send/mailgun.yaml
- Rate-limit headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset. Mailgun describes X-RateLimit-Reset as 'Unix milliseconds (UTC) until the limit resets', to be used for back-off on 429. The docs say to retry 500s with exponential backoff. A 404 'may be temporal due to eventually-consistent system'. — https://documentation.mailgun.com/docs/mailgun/api-reference/api-overview
- v:<name> attaches custom data. Without templates it is metadata that appears as 'user-variables' in events and webhooks. It is also visible to the recipient in the delivered mail's X-Mailgun-Variables header. Anything over 4KB is truncated in events and webhooks. The SMTP equivalent of v: is the X-Mailgun-Variables header. — https://documentation.mailgun.com/docs/mailgun/user-manual/sending-messages/pass-sending-options
- recipient-variables is a JSON dict keyed by recipient address and referenced as %recipient.key%, with a maximum of 1,000 recipients per batch. Without recipient-variables, a multi-'to' send shows every address to every recipient. — https://documentation.mailgun.com/docs/mailgun/user-manual/sending-messages/batch-sending
- o:tag: up to 3 tags per message, case-insensitive, ASCII only, max 128 characters. The default is 100,000 tags per domain (an older FAQ says 4,000 total). — https://documentation.mailgun.com/docs/mailgun/user-manual/tracking-messages/track-tagging
- o:suppress-headers removes X-Mailgun-* headers from the delivered mail ('all' or a comma list). Note: X-Mailgun-Sid is used to process complaints received via feedback loops. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/messages/post-v3--domain-name--messages
- Test mode: o:testmode=yes (SMTP header X-Mailgun-Drop-Message) makes Mailgun accept the message but not send it. It 'will emit a delivered event with a 650 status code', and events carry flags.is-test-mode=true. 'You are charged for messages sent in test mode!' — https://documentation.mailgun.com/docs/mailgun/user-manual/sending-messages/pass-sending-options
- (UNVERIFIED) Whether the 'delivered' WEBHOOK fires for test-mode messages, and whether they count toward the Free plan's 100/day limit, is not stated in the official docs (the event is generated, so webhooks probably fire). — https://documentation.mailgun.com/docs/mailgun/user-manual/sending-messages/test-mode
- Domain tracking API. GET /v3/domains/{name}/tracking returns tracking.open.active, tracking.open.place_at_the_top, tracking.click.active, tracking.unsubscribe.active/html_footer/text_footer and tracking.web_scheme. PUT /v3/domains/{name}/tracking/open takes active (bool) and place_at_the_top. PUT /v3/domains/{name}/tracking/click takes active ('htmlonly'|'true'|'false'). PUT /v3/domains/{name}/tracking/unsubscribe takes active (bool), html_footer and text_footer. All are multipart/form-data. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/domain-tracking/get-v3-domains--name--tracking
- Per-message o:tracking-clicks 'overrides the domain-level click tracking setting' and o:tracking-opens 'has higher priority than domain-level setting'. Links are only rewritten to Mailgun's servers when click tracking is enabled. A single link can opt out with disable-tracking=true. Text-only emails never track opens. — https://documentation.mailgun.com/docs/mailgun/user-manual/tracking-messages/tracking-clicks
- Unsubscribe variables: %unsubscribe_url% (unsubscribes the recipient from everything sent by the domain), %tag_unsubscribe_url% (from the message's tags only), %mailing_list_unsubscribe_url% (from a mailing list). To use your own footer: enable unsubscribe tracking, remove the text from the domain's HTML and text footers so they are not appended automatically, and insert the variable into the HTML and text bodies. — https://documentation.mailgun.com/docs/mailgun/user-manual/tracking-messages/tracking-unsubscribes
- Mailgun adds List-Unsubscribe plus 'List-Unsubscribe-Post: List-Unsubscribe=One-Click' ONLY when (1) the message does NOT already contain a List-Unsubscribe header, AND (2) the domain has unsubscribe tracking enabled OR the request includes the unsubscribe variable. The auto header contains a mailto:u+...@<domain> and/or https://<tracking-host>/u/... URL. If you set your own List-Unsubscribe, Mailgun support will not help troubleshoot it. — https://help.mailgun.com/hc/en-us/articles/203306610-Unsubscribe-Handling-Links
- Enabling unsubscribe tracking requires the tracking CNAME record (the domain verification table lists the CNAME as 'Required for Mailgun to track clicks, opens, and unsubscribes', target mailgun.org). PUT /v4/domains/{name} takes web_scheme ('http'|'https', default http, and https needs a valid cert, generated with POST /v2/x509/{domain}) and web_prefix (the tracking subdomain prefix; the CNAME must match). — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/domains/put-v4-domains--name-
- RFC 8058: 'The List-Unsubscribe header field MUST contain one HTTPS URI', 'List-Unsubscribe-Post ... MUST contain the single key/value pair List-Unsubscribe=One-Click', and the DKIM signature MUST cover both headers. — https://www.rfc-editor.org/rfc/rfc8058.html
- Unsubscribe suppression list: GET /v3/{domain}/unsubscribes?limit=(max 1000) with paging.next/previous/first/last URLs. Items have address, tags (tags of the message the user unsubscribed from) and created_at (RFC822). There are equivalent /bounces and /complaints lists. Mailgun itself will not deliver to addresses that have hard-bounced, unsubscribed or complained. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/unsubscribe/get-v3--domainid--unsubscribes
- GET /v3/{domain_name}/events is DEPRECATED: 'This API is deprecated in favor of our Logs API.' It still documents a message-id query filter, limit max 300, and begin/end in epoch seconds. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/events
- Logs API: POST {base}/v1/analytics/logs with a JSON body: start/end (RFC 2822), duration (listed as required, format '1d'/'2h', overrides start), events[], filter.AND[{attribute, comparator, values:[{label,value}]}], include_totals, pagination{sort:'timestamp:asc', token, limit (max 100)}. The filter attributes include domain, message_id ('ties together the accepted, delivered, and any failed events'), recipient, tag, user_variables, event and severity. Comparators are =, !=, contains, 'not contains', <, <=, >, >=. Items include event, '@timestamp', message.headers.message-id, recipient, flags.is-test-mode and user-variables. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/logs/post-v1-analytics-logs

## Gotchas

- Mailgun does NOT dedupe on Message-ID and has no idempotency key for /messages. A retry after an ambiguous timeout or crash can deliver twice. The dedupe has to be ours: persist the claim and Message-ID before the POST, and reconcile through the Logs API before any retry.
- The response 'id' has angle brackets ('<...@domain>'), but events, webhooks and Logs show message-id WITHOUT brackets. Normalise by stripping <> before storing or comparing. Keep the bracketed form for In-Reply-To and References.
- The Events API (GET /v3/{domain}/events) is officially deprecated. Build reconciliation and catch-up on POST /v1/analytics/logs (JSON body, RFC 2822 dates, pagination tokens, limit max 100). Its schema lists 'duration' as required even though the example omits it, so send start and end, and add duration if you get a 400.
- Log retention on the cheap plans is only 1 day (Free and Basic), and 5 days on Foundation. If the PC is off longer than that, missed events are gone forever. Missing events after that window are NOT proof that a send failed. Use the suppression lists (bounces, unsubscribes, complaints), which do not expire, as the main catch-up source.
- Events are indexed late and out of order (Mailgun's advice: only trust pages older than about 30 minutes). A Logs lookup that finds nothing a few minutes after a crash does not prove the message was not accepted.
- If we set h:List-Unsubscribe ourselves, Mailgun will NOT add its own List-Unsubscribe or List-Unsubscribe-Post (one-click) headers. Do not set List-Unsubscribe; let Mailgun add it.
- Mailgun's unsubscribe links (the footer variable and the List-Unsubscribe URL) live on the tracking CNAME host (default prefix 'email.'). That host needs the CNAME DNS record. Gmail/Yahoo one-click (RFC 8058) needs HTTPS, so set web_scheme=https after generating the tracking cert (POST /v2/x509/{tracking-host}). The default is http.
- If the domain-level unsubscribe footers (html_footer/text_footer) are left at their defaults, Mailgun appends its own footer as well as ours. They must be blanked in the Control Panel under 'Customize unsubscribe templates' or via PUT /v3/domains/{d}/tracking/unsubscribe. Whether the API accepts an empty string is not documented; verify with GET /tracking afterwards.
- Not documented, so verify during setup: whether per-message o:tracking=no (the umbrella switch) also stops unsubscribe-variable substitution. To be safe, send only o:tracking-clicks=no and o:tracking-opens=no, not o:tracking=no. Then check the raw headers of a test email to the owner for List-Unsubscribe, List-Unsubscribe-Post, an HTTPS unsubscribe URL, and no rewritten links.
- Test mode is billed and still produces a 'delivered' event with code 650 and flags.is-test-mode=true. Webhook and reconciliation code must ignore or segregate is-test-mode events so they never mark real people Delivered. Use app-level dry run for development and test mode only for integration checks.
- v: user variables appear in plain view in the recipient's raw headers (X-Mailgun-Variables). Only put opaque IDs there (send_id, campaign_id, step), never internal notes or names like 'cold-list'. Never pass o:suppress-headers=all, because X-Mailgun-Sid is needed to process feedback-loop complaints.
- Max 3 o:tag values per message, ASCII only, max 128 characters. Keep tags low-cardinality (e.g. 'outreach', 'step-1'). Put per-send IDs in v: variables, never in tags.
- Mailgun's AUP forbids non-transactional email without 'clear, explicit and provable consent' and forbids scraped lists. Cold B2B outreach can get the account suspended. The AUP thresholds are stricter than the spec's defaults (complaints ≤0.08% vs the spec's 0.1%; bounces ≤5%).
- A new Mailgun account may be held to about 100 messages/hour, or disabled, until business verification is completed in the Control Panel. The worker must surface this 'business verification is required' error clearly and pause, not retry forever.
- 429 on /messages means the request was rejected (not accepted), so it is safe to retry after back-off. Read X-RateLimit-Reset (documented as Unix ms) and also parse 'try again after N seconds' from the message. A timeout, network error or 5xx is AMBIGUOUS: the message may already be queued at Mailgun.
- The domain region is fixed when the domain is created. EU and US data (events, suppressions, routes, webhooks) are separate, so every API call (messages, logs, suppressions, tracking, webhooks) must use the base URL for the domain's region.
- o:deliverytime scheduling is capped at 3 to 7 days, and cancelling means deleting ALL queued mail for the domain (DELETE /v3/{d}/envelopes on the storage host). Do not use it, otherwise the 'Pause all sending' switch could not stop mail already handed to Mailgun.
- The Custom Message Limit is monthly, account-wide and per region, and it disables the WHOLE account when hit (with a small overshoot). It is a backstop only. The app must enforce its own daily and per-sender caps.

## Plan implications

- Build a provider-agnostic EmailTransport interface in the worker with three modes: DryRun (log only, the default in dev), MailgunTestMode (real API call with o:testmode=yes, used sparingly because it is billed), and MailgunLive. The provider can then be swapped if Mailgun's AUP becomes a problem.
- Implement MailgunClient with Node 24 fetch + FormData (no SDK). baseUrl = region==='EU' ? 'https://api.eu.mailgun.net' : 'https://api.mailgun.net'. Header: Authorization: 'Basic ' + Buffer.from('api:'+key).toString('base64'). Use AbortSignal.timeout(30000). One recipient per request, never batch or recipient-variables.
- Per send, build the fields: from='Sender Name <sender@send-domain>', to='Person <email>', subject (follow-ups: 'Re: <original subject>'), text, html (minimal <p>/<a>), h:Message-Id='<{sendUuid}@{sendingDomain}>', h:Reply-To (only if it differs from From), plus h:In-Reply-To and h:References='<id1> <id2> ...' on follow-ups. Also o:tracking-clicks=no, o:tracking-opens=no, o:tag='outreach' and o:tag='step-N', v:send_id, v:campaign_id and v:step. Do NOT send o:deliverytime, o:testmode (except in test mode), h:List-Unsubscribe or o:suppress-headers.
- Crash-safe send state machine in the DB: queued -> sending (claimed atomically in a transaction together with the pre-generated messageId and claimedAt) -> accepted (on 200; store the response id) | retry_wait (on 429; nextAttemptAt comes from X-RateLimit-Reset or 'after N seconds'; the same Message-ID is reused) | failed_permanent (on 400) | unknown (timeout, network error, 5xx, or found in 'sending' at startup). On 401/403: global pause plus an Owner alert.
- Reconciler for 'unknown' and stale 'sending' rows: POST {base}/v1/analytics/logs with filter AND [domain = sendingDomain, message_id = id without <>] (fallback: user_variables contains send_id), start = claimedAt minus 10 min, end = now, events accepted/delivered/failed. Found -> accepted, plus apply the delivered/failed status. Not found: if under 45 min old, wait and recheck; if the full window was queried successfully and the claim is younger than the plan's log retention, mark 'not_sent' and allow re-queue with the SAME Message-ID. Otherwise mark 'unconfirmed' and ask the Owner or sender to decide in the UI; never auto-resend blindly (the rule is at most one send).
- Startup and hourly catch-up order: (1) GET /v3/domains/{d}/sending_queues and pause if regular.is_disabled; (2) GET /v3/domains/{d}/tracking and warn/pause if open or click tracking is active or unsubscribe tracking is inactive; (3) page through the /v3/{d}/bounces, /unsubscribes and /complaints suppression lists (limit=1000) and upsert flags onto People (this source does not expire); (4) pull the Logs API from lastCursorTime minus 30 min (bounded by plan retention) for delivered/failed/unsubscribed/complained events; (5) reconcile unknown sends; (6) resume sending.
- Settings screen: Mailgun region (US/EU, locked once chosen, with a warning), sending domain, and an 'Account API key (Developer role)' field, used for sending, Logs, suppressions, tracking settings, webhooks, domain verification and validations. Optionally a separate 'Domain Sending Key' used only for POST /messages. Both are stored encrypted and write-only. Add a 'Test connection' button that calls GET /v3/domains/{d}/tracking.
- Mailgun setup wizard/checklist, done by the app via the API where possible: PUT /v3/domains/{d}/tracking/open active=false; PUT /v3/domains/{d}/tracking/click active=false; PUT /v3/domains/{d}/tracking/unsubscribe active=true with empty html_footer/text_footer; POST /v2/x509/{tracking-host}, then PUT /v4/domains/{d} web_scheme=https. Then send a test to the owner's address and have the owner confirm, from the raw headers, that List-Unsubscribe (HTTPS) and List-Unsubscribe-Post are present.
- Footer rendering: our template appends the company name and address plus 'Unsubscribe: <%unsubscribe_url%>' in text and <a href="%unsubscribe_url%">Unsubscribe</a> in HTML. Previews and dry run show the variable as a placeholder. Use %unsubscribe_url% (domain-wide), never %tag_unsubscribe_url%.
- Webhook and Logs processing: key everything by normalised message-id plus user-variables.send_id. Skip or segregate events with flags.is-test-mode=true. Treat Mailgun 'failed' events with reason suppress-bounce / suppress-unsubscribe / suppress-complaint as confirmation that the person is suppressed.
- Health auto-pause defaults: complaints 0.08% (Mailgun's AUP threshold) instead of 0.1%; keep bounces at 3% of the last 200 (stricter than the AUP's 5%). Also auto-pause on 401/403, on a 'business verification is required' error, and on sending_queues.is_disabled.
- Setup guide step: set Mailgun's account Custom Message Limit (PUT /v5/accounts/limit/custom/monthly?limit=N, or in the Control Panel, per region) to about 1.3x the expected monthly volume, as a runaway-loop backstop independent of the app.
- Testing: unit and integration tests use a local fake Mailgun HTTP server (the base URL is configurable). Real Mailgun tests go only to the owner's address, or to sandbox authorized recipients (max 5, activated). The Vitest suite never uses a real key.
