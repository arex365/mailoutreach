## Summary

Mailgun EU asks for five kinds of record: SPF TXT `v=spf1 include:mailgun.org ~all` on the sending domain, DKIM (either one TXT `<selector>._domainkey.<d>` with a 1024- or 2048-bit key, or two CNAMEs `pdk1/pdk2._domainkey.<d>` with Automatic Sender Security), MX `mxa.eu.mailgun.org` and `mxb.eu.mailgun.org` at priority 10, and a tracking CNAME `email.<d>` pointing to `eu.mailgun.org`. The EU hostnames are confirmed by Mailgun's API overview, so the UNVERIFIED mark in mailgun-inbound-validation-domain.md can be dropped. The selector and the DKIM CNAME target vary: the docs show `mx._domainkey`, `s1._domainkey`, `*.dkim1.mailgun.com` and `*.service.mailgun.com`. The checker therefore always compares against `sending_dns_records`/`receiving_dns_records` from `GET /v4/domains/{d}` and never against hardcoded values. The region, the DKIM key size (1024|2048), Automatic Sender Security, the selector and the tracking prefix (`web_prefix`, default `email`) are all chosen when the domain is added. The region can never be changed afterwards.

At 500–1000 emails a day the owner is below every "bulk" threshold (Gmail: close to 5,000 a day to personal Gmail accounts; Microsoft: 5,000+ a day to its consumer domains). Yahoo does not define bulk by volume, and Gmail has been rejecting non-compliant mail since November 2025. So we meet the bulk rules anyway: SPF and DKIM both passing, DMARC at p=none or stronger, From aligned with DKIM/SPF (Mailgun does this automatically when From uses the sending domain), one-click unsubscribe (Mailgun's List-Unsubscribe-Post, see mailgun-sending.md) and a visible unsubscribe link, spam rate under 0.1% (never 0.3%), and valid PTR and TLS (Mailgun's shared IPs handle these).

DMARC is not reported by Mailgun, so the app looks it up itself: `resolveTxt('_dmarc.<d>')`, join each record's chunks with '', keep records starting `v=DMARC1`, and require exactly one. If there is none, walk up to the parent (RFC 9989 tree walk; the subdomain inherits the parent's `sp=`, falling back to `p=`). The checker uses two separate Resolvers (1.1.1.1 and 8.8.8.8). A single Resolver with both servers does NOT fall back on NOTFOUND.

A new domain should be at least 30 days old before campaigns (Mailgun help center, seen only via search) and warmed up slowly (Gmail). Google Postmaster Tools (verification TXT) is worth adding but shows nothing at low volume. Microsoft SNDS is IP-based and can't be used on Mailgun's shared IPs. Cloudflare Registrar sells at cost with no markup, forces Cloudflare DNS, and supports .com/.net/.org/.co/.io/.studio/.design/.agency/.me/.xyz/.uk but not .de/.eu/.art/.pk. A .com costs about $10.44/yr, rising to about $11.15 from 1 Nov 2026 (third-party figures).

### 3. DMARC, SPF, DKIM, MX, CNAME lookups

- DMARC is now **RFC 9989** (May 2026, obsoletes 7489; reporting is in RFC 9990/9991). Policy discovery is a DNS Tree Walk: query `_dmarc.<author domain>`, then go up one label at a time, at most 8 queries. "Records that do not start with a 'v' tag that identifies the current version of DMARC are discarded. If multiple DMARC Policy Records are returned for a single target, they are all discarded." Tags: `p` (none|quarantine|reject), `sp` (subdomain policy, defaults to `p`), `np` (non-existent subdomains, defaults to `sp`, then `p`), `adkim`/`aspf` (default `r` relaxed), `rua`, `ruf`, `fo`, `t` (test, default n), `psd` (y|n|u). **Removed: `pct`, `rf`, `ri`.** If `p` is missing or invalid: act as `p=none` only if `rua` holds a valid URI, otherwise no DMARC. — https://datatracker.ietf.org/doc/html/rfc9989
- External rua destinations: if the rua domain differs from the policy domain, the receiver checks for a TXT record `<policy-domain>._report._dmarc.<destination-domain>` starting `v=DMARC1`. If it is absent, "the URI MUST be ignored". — https://datatracker.ietf.org/doc/html/rfc9990
- Mailgun's recommended start: `v=DMARC1; p=none` at `_dmarc.<domain>`, then tighten after reading reports (see mailgun-inbound-validation-domain.md). Microsoft's fix page uses the same value.
- SPF (RFC 7208): §4.5: discard records not starting exactly `v=spf1`; more than one remaining means **permerror**, zero means **none**. §4.6.4: `include`, `a`, `mx`, `ptr`, `exists` and `redirect` count toward the **10** DNS-lookup limit; `all`, `ip4`, `ip6` and `exp` don't; void lookups (NXDOMAIN or empty) are limited to 2. §3.3: multiple strings in one TXT record "MUST be treated as if those strings are concatenated together without adding spaces." — https://www.rfc-editor.org/rfc/rfc7208.html
- node:dns (Node 24): `new Resolver({timeout, tries (default 4), maxTimeout})`. `setServers(['1.1.1.1'])`. "if attempting to resolve with the first server provided results in a NOTFOUND error, the resolve() method will not attempt to resolve with subsequent servers ... Fallback DNS servers will only be used if the earlier ones time out or result in some other error." `resolveTxt` → `string[][]` (chunks of one record per sub-array); `resolveMx` → `[{priority, exchange}]`; `resolveCname` → `string[]`; `resolve*` always queries the network (not hosts/OS). The error codes are strings: `ENOTFOUND` (NXDOMAIN), `ENODATA` (name exists, no record of that type), `ETIMEOUT`, `ESERVFAIL`, `EREFUSED`, `ECONNREFUSED`, `ECANCELLED`. — https://nodejs.org/api/dns.html
- Observed: `_dmarc.<nonexistent>` → `ENOTFOUND`; `resolveCname` on a name that is not a CNAME → `ENODATA`; `resolveTxt` **follows CNAMEs** (so `resolveTxt('pdk1._domainkey.<d>')` would return Mailgun's key, not prove the customer's record); `_dmarc.mailgun.com` comes back as 3 chunks. Querying an authoritative server directly (resolveNs → resolve4 → a Resolver pointed at that IP) works from this PC. One `ETIMEOUT` was seen with `tries:1, timeout:3000`, so use `timeout:4000, tries:2`.
- DKIM key size can be read from the published key: `crypto.createPublicKey({key: Buffer.from(p,'base64'), format:'der', type:'spki'}).asymmetricKeyDetails.modulusLength` → 1024|2048 (the base64 `p=` is 216 or 392 characters). Checked locally.
- Propagation: Cloudflare says zone changes "take effect globally within 5 minutes", with proxied records at TTL Auto = 300 s. Cloudflare's default SOA Minimum TTL is 1800 s, which is the negative-caching time: a lookup made *before* the record existed can keep returning "not found" at 1.1.1.1/8.8.8.8 for up to 30 min. polygonparadise.com (GoDaddy) was observed with minttl 600. Mailgun itself says 24–48 h and keeps its own `cached` values. — https://developers.cloudflare.com/dns/faq/ · https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/
- Cloudflare: only A/AAAA/CNAME can be proxied, and a proxied record answers with Cloudflare anycast IPs, not the CNAME target. Verification and email-related CNAMEs "should not be proxied". TXT values over 255 characters are split into several quoted strings automatically. — https://developers.cloudflare.com/dns/proxy-status/ · https://developers.cloudflare.com/dns/faq/
- Cloudflare Email Routing, if switched on for a domain, needs its own MX records (`route1/2/3.mx.cloudflare.net`) and SPF `include:_spf.mx.cloudflare.net`, and "Cannot use Email Routing with external mail servers". — https://developers.cloudflare.com/email-routing/setup/email-routing-dns-records/

### 4. What a new separate domain needs before sending

- Age: "If you have recently purchased your domain, it should be active for at least the last 30 days. Webmails and ISPs associate recently purchased domains with spammers". This is UNVERIFIED wording: the Mailgun help-center article returns 403 to our fetcher and the text was seen only in a search snippet. — https://help.mailgun.com/hc/en-us/articles/1260803448249-Can-you-describe-the-IP-warm-up-process
- Warm-up: Gmail (above) says ramp slowly, starting with engaged recipients. Mailgun's 2026 warm-up article: target the most engaged recipients and "try slowing down your warm-up if ISPs are sending too many emails to the spam folder". The app's warm-up ramp (PLAN) covers this. — https://www.mailgun.com/blog/deliverability/domain-warmup-reputation-stretch-before-you-send/
- Registration date can be read with RDAP. Observed: `https://rdap.verisign.com/com/v1/domain/<d>` returns `events[]` with `eventAction:'registration'` (polygonparadise.com: registered 2024-08-22, GoDaddy, ns57/58.domaincontrol.com). Other TLDs have other RDAP bases (IANA bootstrap `https://data.iana.org/rdap/dns.json`, UNVERIFIED for non-.com).
- Website/redirect: (UNVERIFIED, industry practice, no official source found) a sending domain with no website looks less trustworthy. A redirect to polygonparadise.com is enough. On Cloudflare this is a Redirect Rule (301, e.g. `http*://<d>/*` → `https://polygonparadise.com/`). — https://developers.cloudflare.com/rules/url-forwarding/examples/redirect-all-another-domain/
- Google Postmaster Tools: at https://postmaster.google.com/v2/manage_domains, "Add new domain", adding "either the DKIM (d=) domain or the SPF (Return-Path) domain". Copy the TXT or CNAME it shows into DNS. Usually verified at once, up to 10 min. Subdomains of a verified domain need no separate verification. "Data might be missing if the total number of messages for a given day is too low." — https://support.google.com/mail/answer/9981691
- Postmaster "Compliance status" dashboard: Compliant / Needs work per requirement, for primary domains only. It isn't real time, and fixes can take up to 7 days to show. This is from Google's page as quoted in search results; the page itself was not fetched. — https://support.google.com/a/answer/14668346
- Microsoft SNDS is per IP: "once someone can prove that they own an IP range". Authorization goes through postmaster@/abuse@ of the rDNS domain or RDAP contacts, and there is no domain-level data. The portal moved in 2026 and network access expires 10 months after approval. On Mailgun shared IPs the owner cannot use it. — https://substrate.office.com/ip-domain-management-snds/SNDS/FAQ

## Gotchas

- Never hardcode record values. EU vs US hosts, the DKIM selector (`mx`, `s1`, `pdk1`, or custom), the ASS CNAME target (`*.dkim1.mailgun.com` in the guide vs `*.service.mailgun.com` in the OpenAPI example) and the tracking prefix all come from the API.
- A Resolver given `['1.1.1.1','8.8.8.8']` does not ask 8.8.8.8 when 1.1.1.1 says NOTFOUND. Use two Resolvers for the "spreading" signal. `ENOTFOUND` and `ENODATA` both mean "missing"; `ETIMEOUT`/`ESERVFAIL`/`ECONNREFUSED` mean "couldn't check".
- Negative caching: if the checker (or the owner) looks before the record is saved, public resolvers can keep saying "missing" for up to the zone's SOA minimum (Cloudflare 30 min, GoDaddy 10 min). Optionally query the domain's authoritative nameserver too, to tell "you haven't saved it" apart from "saved, still spreading".
- `resolveTxt` follows CNAMEs, so ASS DKIM rows must be checked with `resolveCname`; otherwise a wrong record can look right.
- Join TXT chunks with `''`, never `' '` (RFC 7208 §3.3). 2048-bit DKIM and long DMARC records arrive split.
- DNS panels that append the zone turn `email.d` into `email.d.d`. If a row is missing, also query the doubled name and say "Type only `email` in the Name box."
- The Cloudflare orange cloud on the tracking or DKIM CNAME hides the CNAME (resolveCname → ENODATA, resolve4 → Cloudflare IPs) and Mailgun can't verify it. MX and TXT can't be proxied.
- Turning on Cloudflare Email Routing (or registrar mail forwarding) on the sending domain replaces or adds MX and SPF records and diverts replies away from Mailgun. It must stay off for d.
- Only one SPF record per name. A registrar's default forwarding SPF must be merged or removed. include:mailgun.org already uses 5 of 10 lookups.
- Two DMARC records at one name, or a record not starting `v=DMARC1`, means no policy at all (RFC 9989 and 7489 agree). Don't generate `pct=` (removed in RFC 9989); `t=y` is its replacement for testing. rua pointing at gmail.com is silently ignored.
- For a separate registrable domain (Q8a) there is no parent fallback: `_dmarc.<d>` must exist. For a subdomain (Q8b, mail.polygonparadise.com), polygonparadise.com has no DMARC today, so the subdomain needs its own record. Adding one at the root would also apply to the owner's Zoho mail.
- Bulk thresholds are measured per provider, and Gmail counts only personal Gmail recipients. The owner's 500–1000/day won't reach them, but Gmail rejects non-compliant mail since Nov 2025 and Yahoo has no volume line, so treat every bulk rule as required.
- Small numbers: 1 complaint in 1,000 sends is 0.1%. Postmaster Tools shows no data at low volume, so the app's own complaint and bounce counters are the real signal.
- Mailgun's DNS advice says don't hide WHOIS contacts, but Cloudflare Registrar redacts WHOIS by default (and redaction is normal under GDPR). This is low impact; nothing to do.
- Mailgun domain region is fixed at creation; a wrong region means deleting the domain and re-adding it. `PUT …/verify` can 429; `POST /v2/x509` can 402 on some plans (which plans is UNVERIFIED).
- Changing `use_automatic_sender_security` later requires re-verification and swapping TXT for CNAME records. Decide it in the Add-domain step.
