# Research (planning, verified 2026-09-22): Mailgun webhooks, Events/Logs API and suppressions: payloads, signature verification, retries, reconciliation after downtime

Collected before the plan was written. Re-verify anything marked UNVERIFIED before relying on it.

## Summary

You register webhooks with these event type names: accepted, delivered, temporary_fail, permanent_fail, opened, clicked, unsubscribed, complained. Mailgun POSTs application/json shaped as {"signature":{"timestamp":"<string>","token":"<50 chars>","signature":"<hex>"},"event-data":{...}}. Inside event-data, both kinds of failure arrive as event "failed". What tells them apart is event-data.severity ("permanent" or "temporary"), plus reason (bounce, generic, old, suppress-bounce, suppress-unsubscribe, suppress-complaint, ...), log-level (info/warn/error) and delivery-status {code, message, description, bounce-type, ...}. To verify a webhook, compute HMAC-SHA256 over timestamp+token (joined with nothing between them) using the HTTP Webhook Signing Key, which is not the API key, and compare the hex result. The signature does NOT cover event-data. The docs call the timestamp check and the token cache optional and give no tolerance value. Mailgun counts a POST as delivered only on 200. On 406 it stops. Any other response (and presumably an unreachable host) triggers retries for about 8 hours: 5m, 10m, 15m, 1h, 2h, 4h. The docs exclude the "delivery notification" from retries, so missed delivered events are never resent. A PC that is off overnight for more than 8 hours will lose webhooks, so reconciliation is required, not optional. The v4 domain webhooks API (POST/PUT/DELETE /v4/domains/{domain}/webhooks, with url plus repeated event_types) lets one URL receive several event types. The v3 API is one type per call, with at most 3 URLs per type. The Events API (GET /v3/{domain}/events) is officially marked "deprecated in favor of our Logs API". The Logs API is POST /v1/analytics/logs with a JSON body {start, end (RFC 2822), events, filter:{AND:[{attribute, comparator, values:[{label,value}]}]}, pagination:{sort:"timestamp:asc", token, limit<=100}}. It returns {items, pagination:{next, previous, first, last, total}}. Log retention depends on plan: Free and Basic 1 day, Foundation 5 days, Scale 30 days. Suppression lists (bounces, complaints, unsubscribes, whitelists under /v3/{domain}/...) never age out and are paged with limit (max 1000) and paging.next URLs. That makes them the source of truth for "never email again". The Logs/Events data only fills in delivered and temporary-failure history. The app needs a Developer-role account API key for logs, suppressions and webhooks, because a Domain Sending Key can only POST /messages.

## Facts

- Webhook event types are accepted, delivered, temporary_fail, permanent_fail, opened, clicked, unsubscribed, complained. The v3 create uses form field `id` (the webhook type, enum 'accepted','clicked','opened','unsubscribed','delivered','permanent_fail','temporary_fail','complained') plus `url`, repeatable, max 3 URLs per type. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/domain-webhooks/post-v3-domains--domain--webhooks.md
- Webhook POST body is application/json with two top-level keys: {"signature": {"timestamp": "1529006854" (string of epoch seconds), "token": "<50-char random string>", "signature": "<hex HMAC>"}, "event-data": {...}}. Events from a subaccount also carry signature.parent-signature. — https://www.mailgun.com/blog/product/same-api-new-tricks-get-event-notifications-just-in-time-with-webhooks/
- Signature verification: concatenate timestamp and token with no separator, run HMAC-SHA256 keyed with the Webhook Signing Key, and compare the hex digest to signature.signature. The official Node sample is crypto.createHmac('sha256', signingKey).update(timestamp.concat(token)).digest('hex') === signature. Caching tokens and checking the timestamp are both described as 'optional'. No tolerance value is given, and the docs warn that delivery delays can occur. — https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/securing-webhooks
- The signing key can be read via GET /v5/accounts/http_signing_key, which returns {message, http_signing_key}. POST /v5/accounts/http_signing_key creates or regenerates it. The signing key is separate from the private API key. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/account-management/get-v5-accounts-http_signing_key
- (UNVERIFIED) In the dashboard: Profile menu (top-right) > API Security shows the HTTP Webhook Signing Key, the Verifications Public Key and the API keys. — https://help.mailgun.com/hc/en-us/articles/203380100-Where-can-I-find-my-API-keys-and-SMTP-credentials
- event-data.event values: 'accepted', 'delivered', 'opened', 'clicked', 'complained', 'unsubscribed', and 'failed' for BOTH permanent_fail and temporary_fail webhooks. Examples: permanent is severity='permanent', reason='bounce', log-level='error', delivery-status.code=550, delivery-status.bounce-type='hard'. Temporary is severity='temporary', reason='generic', log-level='warn', code 421. Complained has log-level 'warn'. Delivered, accepted, opened, clicked and unsubscribed have log-level 'info'. — https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/webhook-payloads
- event-data field paths: event, timestamp (float epoch seconds, e.g. 1770146798.372891), id (22-char string, e.g. 'CCXMjJ7nQi2N3BPigGOdgQ'), log-level, account.id, domain.name, recipient, recipient-domain, message.headers['message-id'] (shown WITHOUT angle brackets, e.g. '20260203192638.000be97f99f8cea1@sample.mailgun.com'), tags (array), user-variables, severity and reason (failed only), delivery-status {code, message, description, attempt-no, retry-seconds, mx-host, enhanced-code, bounce-type, session-seconds, certificate-verified, tls, utf8, first-delivery-attempt-seconds}, flags, envelope, storage. The unsubscribed event also includes client-info and geolocation. — https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/webhook-payloads
- The event id is 'unique within a day'. Docs describe it as the way to recognise events you have already retrieved when time ranges overlap. — https://documentation.mailgun.com/docs/mailgun/user-manual/events/event-structure
- Reason values (official Mailgun Go SDK constants): 'unknown','generic','bounce','espblock','greylisted','blacklisted','suppress-bounce','suppress-complaint','suppress-unsubscribe','old','hardfail'. Severity values: 'temporary','permanent','internal','unknown'. Other event names include 'rejected','stored','dropped'. The SDK types user-variables as `any`. — https://pkg.go.dev/github.com/mailgun/mailgun-go/v5/events
- Retries: on HTTP 200 Mailgun treats the POST as successful and does not retry. On 406 it treats the POST as rejected and does not retry. For any other code it retries on this schedule (current docs): 5 min, 10 min, 15 min, 1 h, 2 h, 4 h, over an 8-hour window, 'for Webhooks other than the delivery notification'. — https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/webhook-retries
- (UNVERIFIED) An older doc and help-center wording gives a different schedule: 10 min, 10 min, 15 min, 30 min, 1 h, 2 h, 4 h. It likewise excludes the delivery notification. — https://help.mailgun.com/hc/en-us/articles/202236504-Webhooks
- (UNVERIFIED) The webhook response timeout is not documented officially. Third-party sources (Hookdeck, PostHog PR #103057) state that retries resend the ORIGINAL signature block (same timestamp and token). — https://github.com/PostHog/posthog/pull/103057
- Webhooks can be set at domain level or account level. The limit is 3 URLs per event type. The same URL for the same event at both levels is deduplicated and sent once. HTTPS endpoints need a trusted CA certificate (no self-signed). US and EU regions are configured separately. — https://documentation.mailgun.com/docs/mailgun/user-manual/webhooks/configuring-webhooks
- v3 domain webhooks: GET /v3/domains/{domain}/webhooks returns {"webhooks": {"delivered": {"urls": [...]}, ...}}. Also POST /v3/domains/{domain}/webhooks (form: id, url), plus GET, PUT (form: url) and DELETE on /v3/domains/{domain_name}/webhooks/{webhook_name}. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/domain-webhooks
- v4 domain webhooks: POST /v4/domains/{domain}/webhooks takes application/x-www-form-urlencoded fields `url` (required) and `event_types` (repeat it for each type; enum includes complained) and associates one URL with several event types. PUT /v4/domains/{domain}/webhooks replaces that URL's event-type associations. DELETE /v4/domains/{domain}/webhooks?url=...&url=... removes the URL(s) from all event types. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/domain-webhooks/post-v4-domains--domain--webhooks.md
- Account webhooks: GET/POST/DELETE /v1/webhooks and GET/PUT/DELETE /v1/webhooks/{webhook_id}, with fields url, event_types and description. Bulk DELETE takes webhook_ids or all. Changes 'can take up to 10 minutes to become effective due to caching'. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/account-webhooks
- The Events API reference says 'This API is deprecated in favor of our Logs API.' GET /v3/{domain_name}/events accepts begin and end (epoch seconds), ascending, limit (max 300), event, message-id, recipient, tags, severity, from, to, subject, list, attachment, size. Responses are paged with paging.next and paging.previous. Retention is 'at least 3 days' (plan-dependent). No sunset date was found. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/events/get-v3-domain_name-events
- Event polling guidance: events are stored out of order because they are written by many hosts. Treat a page as trustworthy only if its last event is older than a threshold age (e.g. half an hour). Otherwise discard the page, wait at least 15 s, and repeat. — https://mailgun-docs.redoc.ly/docs/mailgun/user-manual/events/
- Logs API: POST https://api.mailgun.net/v1/analytics/logs (EU: https://api.eu.mailgun.net/v1/analytics/logs), Basic auth, JSON body. Fields: start and end (RFC 2822 strings; end defaults to now, start to 1 day before), duration ('1d','2h'; if set it is counted back from end and overrides start), events (string[]), metric_events, filter {"AND":[{"attribute","comparator","values":[{"label","value"}]}]}, include_subaccounts, include_totals, pagination {sort:'timestamp:asc'|'timestamp:desc', token, limit (max 100)}. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/logs/post-v1-analytics-logs.md
- Logs filter attribute enum includes: id, domain, ip, ip_pool, recipient_domain, recipient_provider, country, bot, device, subaccount, event, attachment_filename, from, message_id, subject, mailing_list_address, to, size, recipient, tag, severity, user_variables, delivered_at, delivery_status_code, delivery_status_bounce_type, delivery_status_message, is_routed, recipients. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/logs/post-v1-analytics-logs.md
- (UNVERIFIED) Filter comparators are '=', '!=', 'contains', 'not contains', and only AND is supported (no OR). These are documented for the Metrics API. The Logs reference uses the same filter shape but does not list its comparators. — https://documentation.mailgun.com/docs/inboxready/api-reference/optimize/mailgun/metrics/filters
- Logs response: {start, end, items[], pagination {previous, first, last, next, total}, aggregates}. Item fields: id, event, '@timestamp' (string), account, domain.name, recipient, recipient-domain, message.headers {to, message-id, from, subject}, delivery-status {code, message, description, attempt-no, bounce-type, retry-seconds, enhanced-code, mx-host, last-code, last-message, ...}, severity, reason, log-level, user-variables, tags, flags {is-test-mode, is-delayed-bounce, ...}. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/logs/post-v1-analytics-logs.md
- The official mailgun.js 14.0.1 typings declare Logs items with 'user-variables' as a STRING (webhooks deliver an object). They also include '@timestamp', and the SDK exposes mg.logs.list({start, end, events, filter, pagination}). Its webhooks client only wraps v3: create(domain, id, url, test?). — https://cdn.jsdelivr.net/npm/mailgun.js@14.0.1/Types/Types/Logs/Logs.d.ts
- Log retention by plan: Free 1 day, Basic 1 day ($15/mo, 10k emails/mo), Foundation 5 days ($35/mo, 50k/mo), Scale 30 days ($90/mo, 100k/mo). — https://www.mailgun.com/pricing/
- Bounces: GET /v3/{domain_name}/bounces?limit=(default 100, max 1000)&page=(next|previous|last)&term=(address prefix) returns {items:[{address, code, error, created_at (RFC822)}], paging:{previous, first, next, last}}. Also GET and DELETE /v3/{domain}/bounces/{address}; POST /v3/{domain}/bounces (JSON array of up to 1000 records {address, code, error, created_at}, or a single form-data record); POST /v3/{domain}/bounces/import (CSV up to 25MB); DELETE /v3/{domain}/bounces clears all. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/bounces/get-v3--domainid--bounces.md
- Complaints: the same endpoint set at /v3/{domain_name}/complaints (list with limit/page, get/delete by address, POST up to 1000 JSON records, CSV import, clear all). Items are {address, created_at}. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/complaints
- Unsubscribes: /v3/{domain_name}/unsubscribes. Items are {address, tags[], created_at}. GET accepts limit (default 100, max 1000), page (next|previous|last), address (the page divider) and term. POST takes a JSON array of up to 1000 {address, tags, created_at}, where tags ['*'] means all tags, or a single form-data record. DELETE /v3/{domain}/unsubscribes/{address} resumes delivery. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/unsubscribe/post-v3--domainid--unsubscribes
- Allowlist: /v3/{domain_name}/whitelists (POST address or domain, plus optional reason; GET list with limit/page; GET/DELETE /{value}; CSV import). An allowlisted address is only kept off the BOUNCE list. — https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/allowlist
- Unsubscribe placeholders: %unsubscribe_url% (whole domain), %tag_unsubscribe_url% (per tag), %mailing_list_unsubscribe_url%. Unsubscribe tracking must be enabled in the domain settings. — https://documentation.mailgun.com/docs/mailgun/user-manual/tracking-messages/tracking-unsubscribes
- Rate limits are reported in X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset headers, with HTTP 429 when exceeded ('Retry as defined in response headers'). Time windows vary by API. The only published number is for the Metrics API: 500 requests per 10 s. — https://documentation.mailgun.com/docs/mailgun/api-reference/api-overview.md
- RBAC: the Developer role has Read/Write on Messages, Logs, Bounces, Complaints, Unsubscribes, Whitelist, Webhooks, Domains, Routes and Validations. Domain Sending Keys 'only allow sending messages via a POST call on /messages and /messages.mime'. — https://documentation.mailgun.com/docs/mailgun/user-manual/api-key-mgmt/rbac-mgmt.md

- Delayed bounces (NDRs) are tracked only if the sending domain's MX records point to Mailgun. Complaints need ESP feedback loops. — https://documentation.mailgun.com/docs/mailgun/user-manual/tracking-messages/tracking-failures

## Gotchas

- Both failure webhook types (permanent_fail and temporary_fail) arrive with event-data.event === 'failed'. You must branch on event-data.severity ('permanent'|'temporary'), not on the registration name.
- The HMAC covers only timestamp+token, NOT event-data. Single-use tokens are the only thing stopping a captured signature block from being reused with a forged body.
- signature.timestamp is a STRING, while event-data.timestamp is a FLOAT in epoch seconds. Logs items use '@timestamp' as a date string instead. Build the HMAC from the exact string received.
- Retries: Mailgun only treats exactly 200 as success (docs say 200, not '2xx'), so return 200 rather than 202/204. 406 stops retries permanently.
- Docs exclude the 'delivery notification' from retries, so delivered webhooks missed while the PC or tunnel is down are never resent. The retry window for other events is about 8 hours, so an overnight shutdown can lose even bounces and complaints from webhooks. Reconciliation is mandatory.
- If retries reuse the original timestamp and token (reported by Hookdeck and PostHog, not in the official docs), a tight freshness window such as 5 minutes would reject every retry. Also, storing the token before processing succeeds would make a legitimate retry look like a replay.
- Two retry schedules exist in Mailgun's own material (5m/10m/15m/1h/2h/4h vs 10m/10m/15m/30m/1h/2h/4h). Both total roughly 8 hours, so don't hard-code either.
- The event id is only 'unique within a day'. Use a composite dedupe key (id plus event date or timestamp), not id alone.
- message-id in events and webhooks has no angle brackets, but the send response id probably does. Normalize by stripping <> and lowercasing before storing or matching.
- user-variables varies by source: an object in webhooks, [] in some doc examples, and typed as a JSON string in the official JS SDK's Logs types. Parse defensively.
- The Events API (/v3/{domain}/events) is deprecated in favour of the Logs API (/v1/analytics/logs) with no published sunset date. A search result claiming the Logs API is deprecated in favour of Metrics is wrong: it is the old Stats API that Metrics replaces.
- The Logs API is account-wide (logs are no longer domain-specific), so always add a filter {attribute:'domain', comparator:'=', values:[{label:D, value:D}]}. Its schema marks 'duration' as required, but the official SDK omits it. Send start+end, and fall back to end+duration if a 400 comes back.
- Logs pagination.limit is max 100, Events API limit max 300, suppression lists max 1000.
- Events and logs can be indexed late or out of order. Never advance a sync cursor past about now-30min, even though you process newer events immediately.
- Retention on Free and Basic is only 1 day. 500-1000 emails/day (15-30k/month) exceeds Basic's 10k/month anyway. Foundation gives only 5 days, so a PC off for more than about 5 days loses delivered and temporary-failure history. Suppression lists are permanent and unaffected.
- A failed event with reason 'suppress-bounce', 'suppress-unsubscribe' or 'suppress-complaint' means Mailgun dropped a send to an address it had already suppressed. Counting these as new bounces would inflate the 3% bounce auto-pause metric.
- A tag-level unsubscribe (%tag_unsubscribe_url%) only blocks messages carrying that tag at Mailgun. Only tags ['*'] means all. The app must treat ANY unsubscribe record as global.
- Suppression lists are per sending domain. Also, the list endpoints' paging.next URL is always present, so stop when items is empty. This is known Mailgun behaviour and matches the Events doc note that requesting past the end of the data returns empty pages; for suppressions it is not stated explicitly.
- A Domain Sending Key cannot read logs, suppressions or webhooks. The worker needs an account API key with the Developer role (or Admin).
- Webhook configuration is separate per region (US vs EU), and the API base URL must match: api.mailgun.net vs api.eu.mailgun.net. Account-webhook changes can take up to 10 minutes to take effect.
- The endpoint needs a publicly trusted certificate. The Cloudflare Tunnel hostname provides one, but Cloudflare Access, and possibly Bot Fight Mode or WAF challenges (unverified), must be bypassed for the webhook path.
- Complaints only arrive from ESPs with feedback loops (e.g. Yahoo, Microsoft), so the complaint rate is under-reported, notably for Gmail.
- Keep v: user variables small (ids only). Anything over 4KB is truncated in events and webhooks.

## Plan implications

- Register ONE domain-level webhook URL, e.g. https://<tunnel-host>/api/webhooks/mailgun. In Settings, add a 'Register webhooks' button. It calls GET /v3/domains/{domain}/webhooks to show the current state, then POST (or PUT if the URL already exists) /v4/domains/{domain}/webhooks with form fields url=... and event_types repeated for delivered, permanent_fail, temporary_fail, complained, unsubscribed. accepted, opened and clicked stay off because tracking is disabled.
- Store the signing key encrypted. Offer a 'Fetch from Mailgun' button that calls GET /v5/accounts/http_signing_key with the Developer API key, so the owner doesn't have to copy it by hand.
- Webhook route handler (Next.js route, excluded from app auth and Cloudflare Access): parse the JSON, check the shape with zod, then compute HMAC-SHA256(signingKey, timestamp+token). Compare with crypto.timingSafeEqual on equal-length hex buffers.
- Freshness check: accept timestamps from now-12h to now+5min. That is wider than the 8h retry window, so retries still pass if they reuse the original timestamp.
- Replay protection: keep a WebhookToken table with a unique token column and ~48h retention. Insert the token in the SAME SQLite transaction that stores the raw event, so a failed attempt never burns the token.
- Status codes: 200 on success and on a duplicate token or event. 401 on a bad signature: it is retryable, which gives time to fix a rotated key, and it is logged loudly. 406 on a stale timestamp or unparseable payload. 500/503 on DB errors so Mailgun retries.
- Keep the webhook handler minimal and fast. It only writes an inbound MailgunEvent row (raw JSON, source='webhook') with a unique dedupe key and returns 200. The worker applies events through the same applyMailgunEvent() function that reconciliation uses.
- Normalize webhook event-data and Logs items into one internal shape: {dedupeKey = event id + UTC date of event timestamp, providerEventId, type: delivered|failed|complained|unsubscribed|accepted, severity, reason, occurredAt (event-data.timestamp*1000 or Date.parse(item['@timestamp'])), messageId (strip <>, lowercase), recipient (lowercase), userVariables (object|[]|JSON string, parsed), tags, deliveryStatus {code, message, description, bounceType}, isTestMode (flags['is-test-mode'])}.
- Apply events idempotently with monotonic flags on SendAttempt and Person (deliveredAt, bouncedAt, complainedAt, unsubscribedAt, lastTempFailAt), each set only if currently null. Order doesn't matter and duplicates from webhook+logs are harmless. Permanent failure, complaint and unsubscribe always set the person's do-not-email flag.
- Health auto-pause bounce rate: count only severity='permanent' failures whose reason is NOT suppress-bounce, suppress-unsubscribe or suppress-complaint, and exclude test-mode events. Complaint rate: count complained events.
- Put small v: user variables on every send: v:send_id, v:campaign_id, v:person_id (well under 4KB). Reconciliation can then map events to rows even if the send response was never stored (crash between the API call and the DB write).
- Reconciliation step 1 (event sync, on worker start and hourly, via the Logs API): read the cursor. Set windowStart = max(cursor - 60min overlap, now - planRetention + 1h). If cursor < now - planRetention, record a visible 'event gap' warning in the dashboard. POST /v1/analytics/logs with start/end as RFC 2822 (Date.toUTCString()), events ['delivered','failed','complained','unsubscribed','accepted'], filter AND [domain = sendingDomain], pagination {sort:'timestamp:asc', limit:100}.
- Reconciliation step 2: follow pagination.next tokens until there is no next token or items is empty. Upsert every item through applyMailgunEvent with source='logs', honour 429 with X-RateLimit-Reset back-off, and only after a complete pass set cursor = min(now - 30min, last item time) in one transaction. Reprocessing the overlap is safe because everything is idempotent.
- Reconciliation step 3 (suppressions, same schedule, per sending domain): fully page GET /v3/{domain}/bounces, /complaints and /unsubscribes with limit=1000, following paging.next until items is empty. Upsert into a local Suppression table (type, address lowercased, createdAt, code/error/tags). Set the person flags. Never auto-remove local suppressions when Mailgun's copy disappears; the app is the source of truth.
- Reconciliation step 4 (push local-only suppressions back to Mailgun): addresses marked unsubscribed or Do-not-contact in the app go to POST /v3/{domain}/unsubscribes as JSON arrays of up to 1000 {address, tags:['*'], created_at}, so Mailgun itself blocks them if an app bug ever tries to send.
- Crash recovery for in-progress sends: a SendAttempt stuck in 'sending' is checked with a Logs query filtered by message_id when known, otherwise recipient + time window, matched on user-variables send_id. If an 'accepted' event exists, mark it sent; if nothing is found after the 30-min indexing lag, the send can safely be retried. Order the worker at startup as: event sync, then suppression sync, then in-progress check, then resume sending.
- Put the events source behind an interface (LogsApiSource now, EventsApiSource as a legacy fallback), because the Events API is deprecated and the Logs API is the documented replacement.
- Use a Developer-role account API key for everything. Optionally also store a Domain Sending Key used only for POST /messages to limit the damage if a key leaks. Make the API base URL configurable: https://api.mailgun.net or https://api.eu.mailgun.net.
- Tests (per SPEC): generate signed test webhook payloads locally with the same HMAC function. Cover a valid signature, a bad signature (401), a stale timestamp (406), a duplicate token (200 no-op), temporary vs permanent failure, and suppress-* reasons not counting toward the bounce rate.
- Unsubscribe handling: use %unsubscribe_url% (domain-level, tags '*') rather than %tag_unsubscribe_url%. Treat any unsubscribes record regardless of tags as a global stop.
