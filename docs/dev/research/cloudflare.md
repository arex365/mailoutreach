# Research (planning, verified 2026-09-22): Cloudflare Tunnel (cloudflared) on Windows 11 plus Cloudflare Access in front of the outreach app, with public Mailgun webhook paths

Collected before the plan was written. Re-verify anything marked UNVERIFIED before relying on it.

## Summary

The current cloudflared release is 2026.9.1 (11 Sep 2026). The simplest install is `winget install --id Cloudflare.cloudflared -e`, which runs Cloudflare's own amd64 MSI. Cloudflare's docs only list the GitHub MSI/EXE downloads. Either way the files land in C:\Program Files (x86)\cloudflared. cloudflared never updates itself on Windows. Cloudflare recommends a remotely-managed tunnel, made in the dashboard at Networking > Tunnels, for most use cases. On Windows the local alternative means copying cert.pem and credentials JSON into systemprofile and editing the registry, so the remote tunnel is the clear choice for a non-developer. In an Administrator terminal, `cloudflared.exe service install <TOKEN>` registers an auto-start LocalSystem service named "Cloudflared". Since 2026.7.3 it writes the token to C:\ProgramData\cloudflared\token and runs `tunnel run --token-file`. The service restarts itself 20s after a failure, logs to Event Viewer (source "Cloudflared") and runs without anyone logged in. The app is published with a single route: a one-level subdomain (e.g. outreach.<domain>) pointing to http://127.0.0.1:3000. Use 127.0.0.1 rather than localhost to avoid Windows ::1 failures. Also, `next start` binds 0.0.0.0 by default, so we pass -H 127.0.0.1. On the Free plan the domain must be fully on Cloudflare (nameservers moved). Partial/CNAME setup is Business/Enterprise only and subdomain delegation is Enterprise only. Tunnel is free on all plans. Access needs Zero Trust onboarding (team name, Free plan, payment details entered but not charged), which covers up to 50 users. New orgs default to the "Cloudflare" identity provider limited to account members, so One-time PIN has to be added by hand. Webhooks work like this: a main self-hosted Access app for the hostname with an Allow policy (Include: Emails list), plus a SEPARATE Access app for outreach.<domain>/api/webhooks/* and /api/health with a Bypass/Include/Everyone policy. The more specific path wins and nothing is inherited. Cloudflare's cloudflared-side "Protect with Access" JWT check must stay off on the single route, because bypassed requests carry no JWT. On the zone: keep Bot Fight Mode off, since it cannot be skipped by any rule. Add a free WAF custom Skip rule for /api/webhooks/*, and turn off Email Address Obfuscation, which is on by default and rewrites e-mail addresses in HTML. Limits: 100 MB upload on Free, and the Proxy Read Timeout is now 125 s (not 100 s), changeable only on Enterprise.

## Gotchas

- Proxy Read Timeout is 125 s, not 100 s. It cannot be raised on Free or Pro. Any request that takes longer gets a Cloudflare 524, so long work (imports, AI line generation, Mailgun catch-up) must run in the worker with the browser polling for status.
- Bot Fight Mode can NOT be exempted for a path: WAF Skip, Page Rules and Allow rules have no effect on it. If it is ever turned on, it may challenge Mailgun's webhook POSTs and they will fail. It is opt-in, so keep it OFF on this zone. (An IP Access rule that matches first also prevents it, but Mailgun's source IPs are not a stable thing to rely on.)
- Email Address Obfuscation is ON by default for every new Cloudflare zone. It rewrites e-mail addresses in server-rendered HTML, which this app is full of (contacts, senders). That breaks what users see and can cause React hydration mismatches. Turn it off for the zone, or add a Configuration Rule for the app hostname.
- New Zero Trust orgs (2026) default to the 'Cloudflare' identity provider with 'Restrict to account members' ON, and One-time PIN is no longer added automatically. Staff without Cloudflare accounts cannot log in until the owner adds the One-time PIN provider and selects it on the application.
- Never use 'Login Methods: One-time PIN' as the Include rule on its own, because that lets anyone with any email in. The Include rule must be an Emails list (or Emails ending in).
- Access path wildcards: `/api/webhooks/*` does not cover `/api/webhooks` itself, and query strings are ignored. Keep every webhook URL strictly under /api/webhooks/<something>. Put /api/health as its own exact-path public hostname entry.
- Bypassed requests carry no Access JWT. Turning on the tunnel route's 'Protect with Access' (cloudflared origin parameter `access.required`) on the single hostname route would therefore reject Mailgun webhooks. Either leave it off, or split the tunnel into two path-based routes (webhooks without it, catch-all with it), which is more complex. (Inferred from how Bypass and the access parameter work; not tested.)
- Bypass also disables Access logging. The app must log webhook hits itself and must verify the Mailgun signature on every request.
- Zero Trust onboarding asks for payment details even for the $0 Free plan. The tunnel alone (core dashboard, Networking > Tunnels) is free on all plans, but Access needs the Zero Trust org.
- On the Free plan the domain's nameservers must move to Cloudflare (full setup). CNAME/partial setup is Business+ and subdomain delegation is Enterprise only. A subdomain of a domain whose DNS stays elsewhere cannot be used on Free.
- Only single-level subdomains (outreach.example.com) are covered by free Universal SSL. outreach.app.example.com needs a paid Advanced Certificate.
- The dashboard's Windows command installs a service pointing at wherever cloudflared.exe was run from (the code uses os.Executable). Install via winget or the MSI first, then run `cloudflared service install <TOKEN>` from an Administrator PowerShell, so the service points at C:\Program Files (x86)\cloudflared\cloudflared.exe and not a Downloads folder. The x64 MSI still uses Program Files (x86) (issue #992), and its PATH entry has a trailing '\.'. After installing, open a new terminal so PATH updates.
- cloudflared never updates itself on Windows. Someone must run `cloudflared update` then `net start cloudflared` (Admin), or `winget upgrade --id Cloudflare.cloudflared -e` followed by restarting the service. The effect of a winget/MSI upgrade on the running service was not verified. Versions older than one year are unsupported.
- Cloudflare's Windows registry example for remote tunnels still shows `run --token <TOKEN>`. Services installed with 2026.7.3 or later use `run --token-file C:\ProgramData\cloudflared\token` instead. Don't paste the old form into the registry.
- `next start` binds 0.0.0.0 by default, which exposes plain-HTTP port 3000 on the LAN and can trigger a Windows Firewall prompt. Bind -H 127.0.0.1 explicitly. Point the tunnel at http://127.0.0.1:3000, not http://localhost:3000, to avoid ::1 vs 127.0.0.1 failures on Windows.
- cloudflared keeps idle origin connections for 1m30s, while Node's default server keep-alive is 5 s. The mismatch can cause occasional 502s or resets on reused connections, especially POSTs. Set `next start --keepAliveTimeout 100000` (larger than 90 s). This follows Next.js's own advice for proxies; I did not test it against cloudflared.
- Do not set the route's HTTP Host Header (httpHostHeader). Leaving it empty forwards the public Host, which Next.js Server Actions' Origin check relies on. If it is set to localhost:3000, Server Actions fail unless serverActions.allowedOrigins lists the public host. `next dev` through the tunnel also needs allowedDevOrigins.
- If office staff open the app over plain http://<LAN-IP>:3000, Secure cookies are not set and login breaks. Everyone, office included, should use the https tunnel hostname.
- If the PC sleeps or loses internet, remote users get Cloudflare 1033 (tunnel down) and a stopped Next.js server gives 502. Mailgun retries event webhooks for a while, but the hourly catch-up job is the real safety net.
- The OTP email comes from noreply@notify.cloudflare.com. Corporate link-scanners can use up the code ('This One-Time PIN has already been used'), so staff may need to allowlist that sender.
- Seats: every person who logs in through Access takes one of the 50 free seats until removed. The 51st user is blocked, not billed.
- Free-plan WAF custom rules have no regex (`matches` is Business+). Use `starts_with(http.request.uri.path, "/api/webhooks/")` or `http.request.uri.path wildcard "/api/webhooks/*"`. Free allows 5 custom rules in total.

## Plan implications

- Tunnel type: use ONE remotely-managed tunnel created in the dashboard, installed as a Windows service. The owner's setup doc: (1) Admin PowerShell `winget install --id Cloudflare.cloudflared -e` (or run cloudflared-windows-amd64.msi). (2) Open a new Admin PowerShell and paste the dashboard's `cloudflared.exe service install eyJ...` command. (3) Check that Networking > Tunnels shows Healthy. No config.yml, no cert.pem, no registry edits.
- Tunnel route: one published application route, `outreach.<cloudflare-domain>` to `http://127.0.0.1:3000`, with no path and all origin settings left at defaults (especially HTTP Host Header empty and Protect with Access off).
- Next.js start command, used by whatever process manager runs it: `next start -H 127.0.0.1 -p 3000 --keepAliveTimeout 100000`. The app is never exposed on the LAN, and everyone, office users included, uses https://outreach.<domain>. On the PC itself, http://localhost:3000 is an emergency fallback.
- Route layout: every Mailgun endpoint lives under `/api/webhooks/` (e.g. /api/webhooks/mailgun/events and /api/webhooks/mailgun/inbound). Health is `/api/health` and returns only non-sensitive status (ok, db ok, worker heartbeat age), with no secrets or counts that leak business data. The proxy/middleware allowlists exactly these prefixes as unauthenticated. Everything else requires the app session regardless of Cloudflare Access.
- Access setup doc, done in this order, before adding the tunnel route: (a) add the One-time PIN identity provider. (b) Create reusable policy 'Outreach staff': Allow, Include: Emails = <staff list>. (c) Create reusable policy 'Public webhook bypass': Bypass, Include: Everyone. (d) Create app 'Outreach' for outreach.<domain> (empty path) with policy (b), login method One-time PIN only (uncheck the Cloudflare IdP) and session duration chosen by the owner. (e) Create app 'Outreach public endpoints' with two public hostnames, outreach.<domain>/api/webhooks/* and outreach.<domain>/api/health, and policy (c). The more specific path wins.
- Treat Cloudflare Access as an outer layer only. The app never trusts Cf-Access-Authenticated-User-Email for authorization. Optionally, and off by default, a setting can store the Access team domain and AUD tag. The proxy then verifies Cf-Access-Jwt-Assertion with jose (createRemoteJWKSet on https://<team>.cloudflareaccess.com/cdn-cgi/access/certs; check issuer and audience) on non-public routes when the request came through the tunnel.
- Client IP for login rate-limiting and audit logs: use the `CF-Connecting-IP` header when present and the socket peer is 127.0.0.1 (i.e. via cloudflared), otherwise use the socket address. Treat X-Forwarded-Proto=https as the tunnel signal. Cookies are always Secure, HttpOnly and SameSite=Lax.
- Keep every HTTP request well under 125 s (target under 30 s). Imports, AI line generation, verification and Mailgun catch-up run as worker jobs and the UI polls job status every few seconds. Avoid long-lived SSE and WebSockets to keep things simple.
- Uploads: cap spreadsheet imports well below Cloudflare's 100 MB (e.g. 20 MB). Accept them through a Route Handler (streaming or multipart), not a Server Action, whose default body limit is 1 MB.
- Config: add `PUBLIC_BASE_URL=https://outreach.<domain>` to .env. The Settings page shows the exact webhook URLs to paste into Mailgun (events and inbound route). Set `serverActions.allowedOrigins` to the public host for safety.
- Cloudflare zone hardening checklist in the setup doc: Email Address Obfuscation OFF (or a Configuration Rule for the app hostname). Bot Fight Mode OFF. One WAF custom rule 'Mailgun webhooks' with expression `(http.host eq "outreach.<domain>" and starts_with(http.request.uri.path, "/api/webhooks/"))`, action Skip: All managed rules, All rate limiting rules, Browser Integrity Check, Security Level.
- Health page: the worker polls cloudflared's local readiness endpoint (http://127.0.0.1:20241/ready, trying ports 20241–20245 in turn; 200 means connected and readyConnections>0, 503 means down). It shows 'Remote access tunnel: connected/disconnected' to the Owner and optionally notifies when it has been down for more than N minutes.
- Operations doc: the PC must be set to never sleep. Next.js and the worker must auto-start at boot without a login, like the cloudflared service, or remote users get 502. Update cloudflared monthly (Admin: `cloudflared update` then `net start cloudflared`, check with `cloudflared --version`). Troubleshooting: Event Viewer > Windows Logs > Application (source Cloudflared), the dashboard Live logs tab, and `cloudflared tunnel diag`.
- Mailgun end-to-end test in the setup doc: after setup, run a curl/Invoke-WebRequest to https://outreach.<domain>/api/health from outside (a phone on mobile data). It should return 200 with no Access login page. Then use Mailgun's 'Test webhook' button. Expect a 200 or signature-rejection log entry in the app, not an Access HTML redirect.
