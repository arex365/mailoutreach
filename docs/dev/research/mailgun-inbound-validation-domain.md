# Research (planning, verified 2026-09-22): Mailgun inbound routes, email validation (Mailgun/ZeroBounce/NeverBounce), and domain DNS verification

Collected before the plan was written. Re-verify anything marked UNVERIFIED before relying on it.

## Summary

Routes: POST /v3/routes takes priority, description, expression and action[]. Routes belong to the whole account, not to one domain, and every route is evaluated unless one runs stop(). Filters are match_recipient(regex), match_header(name, regex) and catch_all(). Actions are forward(email or URL), store(notify=URL) and stop().

Plan limits: Free allows 1 route, Basic 5, and Foundation/Scale have "Full access to inbound routing". Message retention is shorter than the docs suggest: the route docs say store() keeps a message "up to 3 days", but the pricing page lists "1 day message retention" on Free and Foundation, none listed for Basic, and "Up to 7 days" on Scale. Log retention is 1 day on Free/Basic, 5 days on Foundation and 30 on Scale. So the worker can only catch up on replies missed while the PC was off if that happens inside about 24 hours on Foundation.

What Mailgun sends: a forward(URL) POST is url-encoded, or multipart/form-data when the mail has attachments. Fields are signature, timestamp, token, subject, sender, from, recipient, message-headers (a JSON string), body-plain, body-html, stripped-text/-signature/-html, plus attachment-count, attachment-N and content-id-map. Message-Id, In-Reply-To and References are not documented as their own fields, so the app must read them from message-headers. A URL ending in "mime" gets body-mime instead of body-plain/body-html. Mailgun retries a failed POST for 8 hours in total; HTTP 200 or 406 stops the retries. The store(notify) POST carries the same fields plus message-url and attachments metadata. A stored message can be fetched later with GET /v3/domains/{d}/messages/{storage_key}, and Accept: message/rfc2822 returns JSON with a body-mime field. The Events API is deprecated in favour of the Logs API (POST /v1/analytics/logs, at most 100 per page), whose items include storage.url (an array) and storage.key. The 'stored' event type exists.

Conflict with the spec: Mailgun's own docs say that when forwarding to an email address you should turn off click, open and unsubscribe tracking at domain level. Otherwise Mailgun changes each forwarded reply, which breaks DKIM, and replies from domains with a strict DMARC policy may be rejected by Gmail. The spec asks to turn Mailgun unsubscribe handling on at domain level. Mailgun has added ARC headers to routed mail since January 2024, which helps.

Validation: GET or POST /v4/address/validate with address and provider_lookup (default true). The response has result (deliverable, undeliverable, do_not_send, catch_all, unknown), risk (high, medium, low, unknown), reason[], is_disposable_address, is_role_address, did_you_mean and engagement. Price is "from $1.20 / 100 validations", or $0.80 on Scale; Foundation and Scale show "5,000 email validations included"; Free and Basic have it as an add-on. Rate limits are unpublished, so handle HTTP 429. ZeroBounce is GET /v2/validate (api_key, email, timeout 3–60 s) with statuses valid, invalid, catch-all, unknown, spamtrap, abuse and do_not_mail. NeverBounce is GET /v4.2/single/check (key, email) with results valid, invalid, disposable, catchall and unknown, and it reports errors inside HTTP 200 responses.

Domain: GET /v4/domains/{name} returns sending_dns_records and receiving_dns_records, each with record_type, name, value, valid, priority, is_active and cached. PUT /v4/domains/{name}/verify re-checks and can return 429. Neither reports DMARC, so the app checks it with node:dns. Records are SPF "v=spf1 include:mailgun.org ~all", DKIM through Automatic Sender Security (CNAMEs pdk1/pdk2._domainkey, 2048-bit, rotated every 120 days), MX 10 mxa.mailgun.org and 10 mxb.mailgun.org, and a tracking CNAME.

Deliverability: Mailgun says a shared IP is fine below 5,000 emails a day and a dedicated IP makes sense above 50k a week, so 500–1000 a day should use a shared IP. Mailgun recommends a subdomain for sending. Mailgun's Acceptable Use Policy requires "clear, explicit and provable consent" for non-transactional email and forbids bought, rented or scraped lists; this is an account risk the owner must understand.

## Gotchas

- CONFLICT WITH SPEC: the spec wants Mailgun unsubscribe handling turned on (domain level) and replies forwarded to each sender's Gmail by a route. Mailgun's route docs say domain-level click, open and unsubscribe tracking modifies forwarded messages and invalidates DKIM, so a reply from a domain with a strict DMARC policy may be rejected or sent to spam at the sender's inbox. ARC (added January 2024) softens this but does not guarantee delivery. There is no documented per-route override (it is still an open feature request). The sending-topic research must settle how to get Mailgun unsubscribe links and List-Unsubscribe headers without domain-level footer injection. Options: our own footer with %unsubscribe_url% and empty domain footers, or relying on o:tag, which reportedly adds List-Unsubscribe (reported in a mailgun-php GitHub issue). Then test with a real reply from a Yahoo or Outlook address.
- Retention mismatch: route docs say store() keeps messages 'up to 3 days', but the pricing page says Foundation has '1 day message retention', Free 1 day, Basic lists none, and Scale 'up to 7 days'. Log retention is 1 day on Free/Basic and 5 days on Foundation. If the PC is off longer than that, a stored reply body can be lost. The forwarded copy in the sender's Gmail is not affected, but the app will not detect the reply.
- Mailgun stops retrying a failed route POST after 8 hours (last retry about 4 h after the previous one). The PC can easily be off overnight in Pakistan time, so the worker's catch-up (Logs API 'stored' events plus the storage URL) is required, not optional.
- Route timestamp freshness: retried POSTs may carry the original timestamp (not documented). A strict 5-minute freshness check could reject every retry. Use a lenient window for inbound, e.g. 24 h, and rely on HMAC plus token replay protection kept for longer than 8 h.
- Message-Id, In-Reply-To and References are not documented as their own POST fields. Parse the 'message-headers' JSON string, a list of [name, value] pairs, with case-insensitive lookup. Header names can repeat, and Mailgun warns about 'subject' vs 'Subject' duplicates.
- body-html is documented as 'an array of all text/html MIME parts', but it usually arrives as a single form value; handle both. A forward URL ending in 'mime' or 'raw-mime' drops body-plain and body-html, so don't name the endpoint path .../mime.
- Accept: message/rfc2822 on the stored-message GET still returns JSON; the raw MIME is in a 'body-mime' field, not the raw response body.
- Events API (/v3/{domain}/events) is deprecated; use the Logs API POST /v1/analytics/logs. In Logs items, storage.url is an ARRAY, not a string. Page size is at most 100 (Events allowed 300).
- Spelling inconsistency in Mailgun docs: the Routes overview says catchall() while the Route Filters page shows catch_all(). Use catch_all() (the documented example) and confirm with GET /v3/routes/match?address=... after creating.
- Routes are account-wide and regex-based. '.' matches any character and matching is unanchored, so write match_recipient("^ali@send\\.example\\.com$"). Case sensitivity is not documented: store sender addresses lowercase.
- Plan route limits: Free allows 1 route and Basic 5. One route per sender plus a domain catch-all limits Basic to about 4 senders.
- Mailgun's validation OpenAPI enum lists result as deliverable/undeliverable/unknown and risk as low/medium/high only, while the guide adds do_not_send, catch_all and risk 'unknown'. Accept all values and map anything unexpected to 'unknown'.
- Provider label differences: Mailgun 'catch_all', ZeroBounce 'catch-all' (hyphen), NeverBounce 'catchall'. ZeroBounce classes role addresses (info@, sales@) as do_not_mail/role_based. A naive mapping would block every 'General inbox' person, which the spec allows.
- NeverBounce returns errors (auth_failure, throttle_triggered, temp_unavail) inside HTTP 200 responses. Always check body.status === 'success' before reading 'result'.
- Setting Mailgun provider_lookup=false turns unverifiable addresses into result=unknown (reason no_data). Leave it at the default (true).
- Mailgun validation rate limits are not published; it only returns 429 when too many requests are active. Keep concurrency low (2–4) with exponential backoff. There are no bulk-job callbacks, so poll for results.
- Mailgun's AUP requires explicit, provable consent for non-transactional email and bans bought or scraped lists. Cold outreach carries a real account-suspension risk. The AUP spam-complaint limit (0.08%) is stricter than the spec's default auto-pause threshold (0.1%), and the AUP bounce limit is 5% (spec default 3% is fine).
- EU MX and tracking hostnames (mxa/mxb.eu.mailgun.org, eu.mailgun.org) come from third-party and help-center snippets only. Don't hardcode them; show the exact values from receiving_dns_records and sending_dns_records.
- GET /v4/domains does not report DMARC. If the sending domain is a subdomain (e.g. mail.polygonparadise.com) with no _dmarc record of its own, receivers fall back to the parent domain's record and its sp= policy.
- A DMARC rua= address on a different domain (e.g. a Gmail address) won't receive reports unless that domain publishes an authorization record, which is impossible for gmail.com. Use an address on the sending domain (needs a route) or a DMARC report service.
- PUT /v4/domains/{name}/verify can return 429. Don't call it on every Settings page load.
- Testing routes: Gmail hides mail whose sender equals the recipient, so test replies must come from a different account than the one the route forwards to. Also check that the forward target isn't on Mailgun's bounce suppression list.
- No documentation found on whether route-forwarded replies count toward monthly sending volume or billing, or whether Mailgun rewrites the envelope sender (SRS).

## Plan implications

- Reply routes are created by the app through the API (Owner button 'Set up reply routes', re-synced whenever a sender's address or real inbox changes). - Use store(notify=URL) for the app, not forward(URL). It carries the same parsed fields plus message-url, so the worker can re-fetch the full message later, and catch-up can find it via 'stored' log events.
- Inbound endpoint /api/webhooks/mailgun/inbound (exempt from login and from Cloudflare Access): read request.formData() (handles both urlencoded and multipart), verify the HMAC, reject reused tokens (store tokens for 48 h), apply a lenient timestamp window (24 h), then insert an InboundMessage row that is idempotent on storage key or Message-Id and queue a 'process-inbound' job. Return 200 quickly, including for duplicates; return 406 only for permanently unacceptable posts (bad signature); return 5xx for transient DB errors so Mailgun retries.

Collect every <id> from In-Reply-To and References and look them up in OutboundEmail.messageId (the id returned by the Mailgun send response). Fall back to the from-address plus recipient (sender user). The timeline snippet uses stripped-text, falling back to body-plain, truncated to about 300 characters.
