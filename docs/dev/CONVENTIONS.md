## Layout

- `src/core/**` — pure logic, no I/O, no `server-only`; shared by web, worker and tests. Unit-test it.
- `src/server/**` — database and network code shared by the web app and the worker. No `server-only` import
  (the worker can't load it), no `next/*` imports.
- `src/lib/**` — web-only server helpers (auth, request, actions); these may import `server-only` and `next/*`.
- `src/app/**` — routes. `(auth)` = signed-out pages, `(app)` = signed-in app (layout has the shell).
- `src/components/**` — React components. `ui/` is shadcn (don't edit).
- `worker/**` — the background worker. `scripts/**` — Node/PowerShell helpers behind the `.bat` files.
- `tests/unit/<area>/*.test.ts`, `tests/integration/<area>/*.test.ts`, `tests/fixtures/**`, `tests/playwright/**`.

## Auth — every entry point checks

- Pages: `const user = await requireUser()` (or `requireOwner()`) from `@/lib/auth/dal` as the FIRST line. The
  `(app)` layout also checks, but layouts don't re-run on navigation, so pages must check too.
- Server Actions (`"use server"` files): each exported function starts with
  `const user = await requireUserAction()` / `requireOwnerAction()` inside `runAction()` (see below).
  Public actions (login, setup, invite, reset) are the only exceptions.
- Route Handlers: `const user = await getUserOrNull(); if (!user) return Response.json({error:"Sign in again."},{status:401})`.
  State-changing route handlers also check `isSameOrigin(request)` from `@/lib/request`.
- `SessionUser` has `id, email, name, role ("OWNER"|"MEMBER"), timeZone, sessionId`.
- Owner-only: settings, API keys, sending domain, limits, users. Members can do everything else (SPEC §1).

## Server Actions

```ts
"use server";
import { runAction, parseInput, UserError, type ActionResult } from "@/lib/action";
import { requireUserAction } from "@/lib/auth/dal";

export async function renameList(input: { id: number; name: string }): Promise<ActionResult<{ id: number }>> {
  return runAction(async () => {
    const user = await requireUserAction();
    const data = parseInput(schema, input);          // throws UserError with fieldErrors
    if (taken) throw new UserError("A list with that name already exists. Pick another name.");
    await dbTx(async (tx) => { /* … */ await logActivity({ actorId: user.id, … }, tx); });
    revalidatePath("/contacts");
    return { id };
  }, "List renamed.");
}
```
- Never throw raw errors to the browser; `runAction` turns them into `{ ok:false, error }` with plain wording.
- Forms using `useActionState`: submit with `useKeepValuesSubmit(dispatch)` from
  `@/components/forms/use-keep-values-submit` (`<form onSubmit={…}>`), NOT `<form action={dispatch}>` — React 19
  clears every field after a form action, so after an error people would have to retype everything.
- Client side: call the action, then `toast.success(res.message)` or show `res.error` (and `fieldErrors`).
- Server Action bodies are limited to 2 MB. File uploads go through a Route Handler.

## Database rules (PLAN.md B5) — important

- Import the client from `@/server/db`: `db` for reads; **all writes via `dbWrite(c => …)` or `dbTx(tx => …)`**
  (per-process write lock + retries for SQLITE_BUSY). Never call `db.<model>.create/update/delete` directly outside
  those. Keep transactions short (≲50 ms); **no network calls inside a transaction**; chunk big work (≤500 rows per tx).
- Types/enums: `import { Prisma, type Company, CompanyStatus } from "@/generated/prisma/client"`.
  Client components that need enum values/labels use `@/core/labels` (don't import the Prisma client in the browser).
- SQLite has no case-insensitive `mode`: search `Company.searchText` / `nameNorm` / `Person.emailNorm` (lowercase,
  accent-free) with `contains` on normalised input. `createMany` has no `skipDuplicates` on SQLite: dedupe in code.
- Soft delete: Company and Person have `deletedAt`. **Every query of companies/people filters `deletedAt: null`**
  unless it deliberately looks at deleted rows. Never hard-delete companies or people (history must survive).
- Automatic status changes use compare-and-set (`updateMany({ where: { id, status: "NOT_CONTACTED" } … })`).
- After changing any field that feeds search (company name/website/domain/instagram/niche/country, any person's
  name/email/role, adding/removing people) call `refreshCompanySearchText(tx, [companyId])` from
  `@/server/company-search` in the same transaction.
- Company fields derived on write: `nameNorm = normalizeCompanyName(name)`; website via `parseWebsite()` →
  `website=url, domain, profileKey`; `priorityRank = priorityRank(priority)` (from companies/filters);
  `country = normalizeCountry()` (server) and `timeZone = defaultTimeZoneFor(country)` unless the user set one;
  whenever `lastEmailedAt` or `importedLastContactAt` is written, also write
  `lastContactAt = lastContactAt(lastEmailedAt, importedLastContactAt)` (from companies/filters): "Last emailed"
  sorts and filters by that column.
- Person fields: `parseEmail(input)` → `email`, `emailNorm` (unique!). If the address is a role address
  (`isRoleAddress`) and no name is given, `name = GENERAL_INBOX_NAME`, `isGeneric = true`.
  `firstName = firstNameFrom(name, isGeneric)`. Changing a person's email clears all six check fields: spread
  `CLEARED_CHECK_FIELDS` from `@/core/verification/types` (status, risk, date, provider, throwaway flag, "no answer" count).
- Log every change with who made it: `logActivity({ actorId: user.id, type, summary, companyId, personId, data }, tx)`
  from `@/server/activity` (types listed there). Summaries are plain sentences: "Ali set status to Client".
- Settings: `getSetting/getSettings/setSetting` from `@/server/settings` (defaults in `SETTING_DEFAULTS`).
  Worker-owned state: `@/server/state` (compare-and-set). Secrets: `@/server/secrets` (never send to the browser).
- Jobs: `enqueueJob()` from `@/server/jobs`; handlers have the `JobHandler` signature; progress via `ctx.progress()`.
- Filters for company lists: `@/server/services/companies/filters` (`parseCompanyFilters`, `buildCompanyWhere`,
  `buildCompanyOrderBy`, `companyFiltersToParams`) — the ONE definition used by Contacts, export and campaigns.

## SQLite transactions (`@/server/db`)

The web app and the worker are two processes on one SQLite file; each process has ONE connection (Prisma's
better-sqlite3 adapter) and a per-process write lock (`withWriteLock`) that `dbWrite` and `dbTx` take.

- **`dbTx` takes SQLite's write lock with its first statement** (`TAKE_WRITE_LOCK`, a no-op
  `UPDATE "SystemState" … WHERE 0`). The adapter's BEGIN is deferred, so without it a transaction that reads before
  it writes failed at once (SQLITE_BUSY / BUSY_SNAPSHOT) whenever the other process was writing. Now it waits in
  SQLite's busy handler (web 2 s, worker 10 s per try; this blocks that process's event loop, as every `dbWrite`
  already did) and `withDbRetry` retries a busy error, including the raw statement's P2010 form. So write your
  transaction in whatever order reads naturally, but remember: **every `dbTx` holds the database write lock for its
  whole length, the reading part too.** Keep it short (≲50 ms), and use plain `db` reads, not `dbTx`, for read-only work.
- Never patch the adapter's BEGIN into `BEGIN IMMEDIATE`: when that BEGIN times out, the adapter never releases its
  own mutex and every later transaction of the process fails.
- **Never start a `dbTx` inside a `dbTx` callback.** The inner one waits for the adapter's mutex that the outer one
  holds: about 50 s of stalling, then the outer transaction fails while the inner one's write is committed. Pass `tx`
  down instead (helpers take a `Tx` / `DbOrTx`). A `dbWrite` inside a `dbTx` doesn't stall, but it runs on the same
  connection inside the open transaction, so it commits or rolls back with it; prefer `tx`.
- **A plain `db` read sees this process's open transaction** (same connection), half-done writes included. Reads that
  must not see half-done work run under `withWriteLock(…)`, which waits for this process's transactions to finish
  (the final check before a send does this). `withWriteLock` is re-entrant within one async flow (AsyncLocalStorage),
  so `dbWrite`/`dbTx` inside it run at once. Inside it (and inside `dbTx`), never await a promise that another flow
  created and that itself needs the lock (it queues behind you: a deadlock), and never make a network call: release
  the lock first (the final check returns before the hand-over to Mailgun).
- **Long runs of chunk transactions** (imports, holds and releases, bulk status changes, clean-ups) pause between
  chunks with `pauseForOtherWriters(heldMs)` (10–50 ms, a quarter of the chunk's lock time), never `setImmediate`, so
  the other process's busy handler gets a turn. Keep chunks at ≤500 rows.
- Tests: `tests/integration/foundations/db-lock.test.ts` (re-entry, serialised read-then-write, what a plain read
  sees), `tests/integration/webhooks/lock-first.test.ts` (two processes), `tests/unit/db/retry.test.ts`.

## UI rules (PLAN.md A6) — reviewers check these

- Dark only. Colours via tokens (`bg-card`, `text-muted-foreground`, `border-border`, `bg-brand`, `text-status-client`…).
- **Orange (`bg-primary` / `<Button>` default variant / `bg-brand`) ONLY for the single primary action of a screen or
  dialog, and for "selected" markers** (active tab underline, selected list bar, ticked checkbox). Every other button is
  `variant="outline" | "secondary" | "ghost"`; destructive actions use `variant="destructive"`. Progress bars, badges,
  switches, links and charts stay neutral. Text on orange is near-black (already set by the theme).
- Sentence case everywhere ("Email these companies", not "Email These Companies"). No ALL CAPS, no `uppercase` class
  on labels.
- Wording from the user's point of view; see the wording table in PLAN.md A6 ("Background sender", "Can't confirm"…).
- Every list/table/queue has an **empty state** with the exact text from PLAN.md A6 where given, and one next-step
  button. Every error says what went wrong and how to fix it; technical codes only behind "Details".
- Status chips always show the word; "Do not contact" also has a blocked icon (`Ban` from lucide).
- Keyboard: everything reachable by Tab, visible focus (global `:focus-visible` outline — don't remove it),
  single-key shortcuts never fire while typing in an input/textarea/select/contenteditable.
- Works on a laptop (1280–1440 px) and a phone (≥360 px): tables collapse to cards or hide low-priority columns.
  A list or card grid that holds truncated or nowrap values uses `grid-cols-1` (minmax(0,1fr)), not the implicit auto
  column, and flex/grid items on the way down get `min-w-0`; unbroken emails in narrow cells get
  `[overflow-wrap:anywhere]` (M6 review SCREENS-04/05/06/08/12). `tests/unit/shell/truncate-chain.ts` checks a
  component's static markup for this pattern; use it for any new list with long values.
- A client form that awaits a Server Action inside `startTransition` catches a thrown action (a lost connection) and
  shows the "Couldn't reach the app, so nothing was saved…" sentence, keeping what was typed (SCREENS-11).
- Look-ups by a value from the URL (`?notice=`, `?tab=`) use `Object.hasOwn` or a Map, never a plain object's `[key]`
  (inherited keys such as `constructor` would resolve; SECURITY-06).
- Copy-to-clipboard: `navigator.clipboard` is missing on the plain-http office address; fall back to a selected
  textarea + `document.execCommand("copy")`, or show the text in a select-all box.
- IDs in the browser: never `crypto.randomUUID()` (not available on http LAN); use server ids or `useId()`.
- Server components by default; `"use client"` only where interaction needs it. After mutations call
  `revalidatePath()` in the action and/or `router.refresh()` in the client.
- Dates shown with `@/core/time/format` in `user.timeZone` (pass it from the server component as a prop).

## Testing

- Unit tests (pure logic): `tests/unit/<area>/*.test.ts`, `import { describe, it, expect } from "vitest"`.
- Integration tests that need a database: create a fresh temp DB per test file:
  ```ts
  import { createTestDb } from "../helpers/test-db"; // tests/integration/helpers/test-db.ts
  const t = await createTestDb(); // sets DATABASE_URL to a new file under data/test/ and applies migrations
  const { db } = await import("@/server/db");      // import server modules AFTER createTestDb()
  ```
  Without `createTestDb()` the database is `data/test/__use-createTestDb__/none.db`, a folder that never exists
  (`tests/setup/env.ts`, M6 L16): a test that queries it fails at once with a path that says why. (A unit test that
  only imports a module which loads `@/server/db` prints a harmless "[db] PRAGMA setup failed" line.)
- Never point tests at `data/app.db`. Never call real Mailgun/Anthropic/websites.
- Run only your own tests: `npx vitest run tests/unit/<area> tests/integration/<area>`.

## M3: Mailgun rules

Milestone 3 added real sending through Mailgun (`docs/dev/M3-DESIGN.md`). These rules keep it safe; reviewers check them.

- **Never call the real Mailgun from tests, scripts or "just looking".** Mailgun's real host names appear only in
  `src/server/mailgun/base-url.ts` (a unit test greps `src/**` and `worker/**`). Tests use the local fake server
  (`tests/fake-mailgun/`): call `connectFakeMailgun()` from `tests/integration/helpers/mailgun.ts` after
  `createTestDb()`. `tests/setup/env.ts` sets `OUTREACH_TEST_RUN=1`, which makes every Mailgun call refuse anything but
  `http://127.0.0.1:<port>`. Only test keys (`key-fake-…`) go to the fake, and the fake gets nothing else. Never use
  the owner's key or database, not even read-only. DNS in tests goes through a fake `DnsLookup`
  (`tests/unit/checks/fake-dns.ts`), and remote-access checks through an injected `fetchImpl`.
- **Get Mailgun through `getMailgunContext()`** (`@/server/mailgun/context`; `clientFor(ctx, region)` for an older
  domain). It answers "not connected" in the practice copy, without a domain or key, or with a key that doesn't fit the
  server. Code that may run in tests takes a `mailgun?: () => Promise<MailgunContextResult>` injection point.
- **No network call inside a transaction** (`dbTx`/`dbWrite`), ever. The send claim is an autocommitted
  compare-and-set before the POST; the POST is never retried and never aborted (not by shutdown, not by a lost lease);
  Mailgun's id (`providerId`) is saved on its own before `markSent`. An unclear outcome (timeout, network, 5xx, 3xx,
  200 without an id) makes the row UNKNOWN for the reconciler: never requeue it yourself.
- **`markSent()` is the only "sent" writer.** Any Mailgun event matched to an email proves it was sent: use
  `ensureSentFromEvent()` / `applyMailEvent()` (`@/server/services/mail-events/apply`), never write `status: "SENT"`.
- **"Counted" vs "emailed":** caps, pacing, warm-up and health use `countsAsReal`/`realModes`; the 30-day rule,
  reservations, company status, `lastEmailed*`/`firstContacted*` and a reply's "changes status" use
  `countsAsEmailed(mode, {practiceCopy, launchedGoLive})` (`@/core/rules/mode`), and database filters use
  `emailedSendWhere(practiceCopy)` (`@/server/services/emailed`). Since M6 "emailed" is judged per campaign by its launch
  flag `Campaign.launchedGoLive`, never by today's switch: LIVE sends of a campaign launched before go-live are counted
  but never "emailed", before or after go-live (see "M6" below).
- **Which rows may go:** only the sending loop's gates send TEST/LIVE rows (`gates.ts` → `sendOneEmail` with
  `gatedEmailId`). The test-list guard runs at launch, in the send-time re-check, in the final check before the POST
  and inside `MailgunClient.sendMessage` (`send-guard.ts`), so no path can skip it; since M6 a campaign email reaches a
  non-test-list address only after go-live and with `SendMessageInput.testListOnly === false` (fail closed). Mode
  blockers come from ONE place, `@/core/sending/mode-gates` (the settings page, the wizard and the launch all show the
  same sentences).
- **Worker-owned state** (SystemState) is read and written only through the parsers in `@/core/system-state-parse`
  with `readTyped`/`updateTyped` (`@/server/state-typed`, compare-and-set). Types live in the contract file
  `@/core/system-state`. Owner-edited values stay Settings; the worker never writes them.
- **Pauses** go through `pauseSending()` / `resumeSending()` (`@/server/services/sending/pause`): the first cause
  wins, later ones go into `also`. A pause stops every mode, dry runs included.
- **Owner notices that could repeat** (Mailgun problems, tunnel down, …) go through `shouldSendNotice(key)` first: at
  most one per key per 24 h. The notice keys are listed in `@/server/notifications`.
- **Errors:** people see `plainMailgunError()` sentences (§5.9 of the design); Mailgun's own text only behind
  "Details". Logs and job errors go through `describeJobError(err, await mailgunSecrets())`, which hides every saved
  key and its `Basic` form.
- **Webhooks** (`/api/webhooks/mailgun/{events,inbound}`) are the only public POST routes: signature, freshness and
  size checks in the order of §4.4.1, answers 200/401/406/500 only, never `isSameOrigin`, and they are allowlisted in
  `tests/unit/security/auth-coverage.test.ts`.
- **Jobs and loops:** a new job type goes in the `JobType` union (`@/server/jobs`) AND in `createJobRegistry()`
  (`worker/jobs/index.ts`), or enqueueing it fails with "Unknown task type". Periodic work goes in `PERIODIC_TASKS`
  (`worker/periodic.ts`); anything that must react within seconds is a loop in `worker/main.ts` (sending 5 s, event
  lane 1 s, reconciler 10 min, monitor 1 min), never a job.
- **Times:** sending hours use each recipient's zone (`@/core/sending/window`), the daily limit uses the cap day
  (`@/core/sending/capday`, Setting `sending.capDayTimeZone`), both DST-safe through Temporal. Never compute days with
  `Date` arithmetic.
- **Manual checks against the fake** (the lead only): `node scripts/fake-mailgun.mjs --port 4010 …` and
  `run-prod.mjs --db <a test database>`, which sets `OUTREACH_TEST_RUN=1` itself (§6.3 of the design). The fake is
  refused on `data/app.db`.

## M4: sequences and replies rules

Milestone 4 added follow-ups, reply processing and notifications (`docs/dev/M4-DESIGN.md`). Reviewers check these.

- **Replies are processed in exactly one function**, `processInboundMessage` (`@/server/services/replies/process`): the
  worker's event lane runs it through `processPendingInbound` (20 per round, a back-off map of 1, 5, 15, 60 minutes, then
  the fail-safe hold), and Simulate reply calls it directly. Webhook routes and the catch-up only **store**
  (`storeInbound`); they never classify, link, stop or notify. A compare-and-set on `processedAt` makes two processes
  harmless.
- **Never follow, fetch or render a link found in a received message** (challenge-response links, tracking links).
  Reply text is plain text only (React escapes it); never `dangerouslySetInnerHTML`.
- **Stops and holds have one door each.** Recipients are stopped only through `stopRecipients` / `stopCompany` /
  `stopCompaniesForStatus` (`@/server/services/mail-events/stops`) and held or released only through
  `@/server/services/sequences/holds` (`holdCompany`, `releaseCompanyHold`, `applyPendingPossibleReplyHolds`,
  `applyOutageHold`, `releaseOutageHold`). Nobody writes `state: "HELD"` or a stop code by hand.
- **Every write that moves a recipient out of HELD also clears `holdReason` and `heldAt`** (skip, cancel, retry, stop,
  fail, finish). Readers use `heldReasonsOf` (`@/core/sequences/hold-reasons`), which ignores the fields unless the
  state is HELD, and the texts come from `holdStateText` / `stopStateText` / `sequenceSuffix`
  (`@/core/sequences/wording`), so the campaign page, Contacts and the company panel say the same thing.
- **Follow-up timing only through `followUpDueAt`** and threading only through `threadHeaders` / `sentIdsOf`
  (`@/core/sending/follow-up`): calendar days in the recipient's zone, then the next open slot for gated emails; never
  `Date` arithmetic. `markSent` (the only "sent" writer) creates the next row; `markSent({onlyFrom})` is how a reply
  proves an UNKNOWN/UNCONFIRMED email was sent (a SENDING or FAILED row is never touched).
- **Reply windows are measured from the message's arrival (`receivedAt`)**, never from processing time, so backlog rows
  and retried rows link to the email that was out when they arrived. A reply's scope and "changes status" are stored
  when it is processed (`replyScope`, `changesStatus`) and every later decision uses the stored values.
- **Our own addresses come from one place**, `internalSenders()` (`@/server/services/mail-events/internal-senders`), used
  by both the send guard and the processor so they agree on what holds nothing (the team, test replies).
- **Notification and activity copy for replies comes from `@/core/replies/copy`** (`replyNotificationCopy`,
  `replyActivitySummary`, `possibleReplyReasons`), the outage hold's from `outageHoldCopy`. Dates in a notification are
  written in the receiving user's `timeZone`; activity summaries carry no dates (the Activity page renders
  `data.from/to` in the viewer's zone). Several users get one notification each through `notifyUsers` (it de-duplicates
  and skips switched-off users).
- **Pop-up groups and list filters come from `@/core/notification-types`** (`POPUP_GROUP_TYPES`, `popupTypesFor`,
  `notificationFilterOf`), so a type is grouped the same way by the bell, the summary route, Settings and the
  Notifications page. Pure pop-up decisions live in `@/core/notifications/popups`; the browser pieces (Notification API,
  localStorage keys `pp.popups.*.<userId>`) in `src/app/(app)/settings/notifications/desktop-popups.ts`.
- **"Replies waiting for an answer" is built from `InboundMessage`** (kind REPLY/POSSIBLE_REPLY/UNLINKED, processed,
  not answered), never from notifications (read ones are deleted after 90 days). Dry-run replies (`replyScope
